# 《开仙门》最小MVP需求文档

版本：v0.1  
目标：把“基础经营 -> 开战 -> 战斗 -> 结算 -> 返回经营”的最小可玩闭环做出来，只保留能验证核心玩法的内容。

## 1. 文档目标

这份文档不是完整设计稿，也不是最终内容表，而是用于确认最小MVP的边界，避免继续把不必要的山峰系统、经营扩展和战斗分支加进来。

## 2. 最小MVP的核心验证点

1. 玩家在经营阶段点击器灵，可以获得灵气。
2. 灵气可以用于修复已经摆好的山峰资源。
3. 山峰修复后可以升级，并选择山峰的功法类型。
4. 进入战斗后，山峰功法会影响器灵的攻击表现。
5. 战斗采用波次推进，击杀怪物获得经验。
6. 升级时可以在战斗中弹出3个增强选项。
7. 战斗结束后回到经营阶段，进入下一轮循环。

## 3. 最小MVP的状态结构

### 3.1 经营阶段

经营阶段只保留这几个动作：

1. 点击器灵，获得10点灵气。
2. 使用灵气修复山峰资源。
3. 山峰修复后可升级。
4. 升级时选择山峰功法类型。
5. 提供“开战”按钮，玩家决定是否进入战斗。

### 3.2 战斗阶段

战斗阶段只保留这几个动作：

1. 点击“开战”后进入战斗。
2. 经营阶段暂停。
3. 器灵依据当前山峰功法进行攻击。
4. 怪物按波次出现。
5. 击杀怪物获得经验。
6. 器灵升级时，立即弹出3个增强选项。
7. 战斗结束后进入结算，再返回经营阶段。

## 4. 经营阶段规则

### 4.1 点击器灵获得灵气

- 玩家每次点击器灵，固定获得10点灵气。
- 这里的灵气是经营阶段的基础资源。
- 不需要扩展成复杂的采集、加成或概率系统。

### 4.2 修复山峰资源

- 灵气可用于修复已经放在场景里的山峰资源。
- 山峰资源必须是美术里已经摆好的资源，不做代码生成山峰的系统。
- 不引入“自动铺山”“随机造山”“程序生成山体”的方案。

### 4.3 山峰升级与功法选择

- 山峰修复完成后，可以升级。
- 升级时可选择山峰功法类型。
- 功法类型决定战斗阶段的攻击方式表现。
- 例如飞剑类型，对应进入战斗后的飞剑攻击形式。

### 4.4 开战按钮

- 经营阶段需要一个明确的“开战”按钮。
- 玩家点击后才进入战斗。
- 不自动切战斗，不强制打断经营。

## 5. 战斗阶段规则

### 5.1 波次规则

- 战斗分10波。
- 第1波固定50只怪。
- 后续波次逐步递增。
- 递增幅度先保持简单明确，优先完成可玩闭环。

### 5.2 经验与升级

- 器灵攻击击杀怪物后获得经验。
- 器灵升级后，立即弹出3个增强攻击技能选项。
- 升级选择应在战斗中随时出现，不等战斗结束。

### 5.3 战斗中的增强选项

以下是飞剑类的示例增强方向：

1. 增强攻击。
2. 变成两个飞剑弹道。
3. 增强穿透。

这部分作为最小MVP的示例池即可，不要求一次把所有职业分支做全。

### 5.4 结算与返回

- 战斗完成后进入结算。
- 结算后返回经营阶段。
- 保持循环清晰，让玩家可以继续修复、升级、再开战。

## 6. 最小MVP不包含的内容

1. 不做完整的大世界山峰系统。
2. 不做代码生成山峰。
3. 不做复杂经营数值链路。
4. 不做战斗外的庞大养成树。
5. 不做过多的怪物类型和波次机制扩展。
6. 不做战斗之外的大量剧情流程。

## 7. 本阶段的目标体验

玩家进入游戏后，能明确感受到：

1. 在经营里点器灵能拿到资源。
2. 资源能修复和提升已有山峰。
3. 山峰功法会影响战斗表现。
4. 玩家主动点击开战后进入战斗。
5. 战斗里能打波次、拿经验、升技能。
6. 打完回到经营，继续下一轮。

这就是本次最小MVP要验证的完整闭环。

## 9. MVP 架构合规检查

```
涉及的核心模块（对照三层架构）：
  表现层：BattleHUD、FloatingText、CardSelectionPanel、RepairPromptPanel、ResultPanel
  逻辑层：GameManager、WaveManager、CardManager、MountainManager、MainPeak、EnemyBase
  数据层：CsvLoader、DataManager、7 个 Resource 类、6 份 CSV

模块间通信：
  - GameManager 为信号中枢，转发所有模块间信号
  - 逻辑层不直接操作 UI 节点（通过信号 → 表现层方法）
  - 数据层不发射 UI 信号

已知架构债务（MVP 范围内）：
  - summon_artifact_sword.gd 有 get_node("Battlefield/MainPeak") 硬编码路径
  - CardManager 有 get_node("Managers/MountainManager") 硬编码路径
  - 自动灵气产出参数（0.2s/+5）硬编码在 game_manager.gd
  - 山峰修复/升级消耗（20/30）硬编码在 repair_prompt_panel.gd
```

## 10. MVP 反模式自查

```
☑ MVP 是否在制造"上帝 Manager"？
  → 部分风险。GameManager 承担了状态机+信号中枢+浮字+灵气产出等多重职责。
     但每个子领域有独立 Manager（Wave/Card/Mountain），边界可识别。

☑ 是否有数据在代码和 CSV 中双轨存在？
  → 是。修复消耗/升级消耗/灵气产出参数仍在代码中，未全部迁入 CSV。

☑ 是否有硬编码路径？
  → 是。CardManager 和 summon_artifact_sword.gd 中有非集中管理的路径引用。

☑ MVP 范围是否得到控制？
  → 是。第 6 节明确列出了 6 条不包含内容，且均未被突破。
     但实际实现已经超越 MVP 范围（6 功法/29 卡牌），文档需同步更新。
```
