# 功能需求文档模板

> 给 AI 实现功能前，按此模板填空。每个格子都写，不确定的写"待定"——比空着让 AI 猜要好。

---

## 1. 功能概述

> 一句话 + 一段话。先给 AI 建立全局概念。

**一句话**：[20 字以内说清这个功能]

**详细描述**：[3-5 句，包含：谁操作、触发什么、最终结果是什么]

**示例**：
- 一句话：玩家点击未修复山峰，消耗灵气进行修复
- 详细描述：在经营阶段（PREPARATION），玩家点击战场上一座未修复的山峰，弹出修复面板。面板显示修复所需灵气消耗。玩家确认后扣除灵气、山峰激活、可开始选择该峰的功法。灵气不足时按钮置灰不可操作。

```

  2. ...
```

**示例（山峰修复功能）**：
```

  1. GameManager — 新增 on_mountain_selected 逻辑、状态切换
  2. MountainManager — 新增 repair 方法、修复状态管理
  3. GameState — 可能需要新增状态或复用 PREPARATION
  4. DataManager — 仅读（读山峰修复消耗配置）

需要新建的模块：
  1. RepairPromptPanel — 修复确认弹窗 UI

不需要动的模块：
  - WaveManager — 战斗阶段不涉及修复
  - CardManager — 修复不涉及卡牌选择
```

## 3. 触发条件与状态约束

> 什么情况下触发？受什么状态限制？

| 维度 | 说明 |
|------|------|
| 触发方式 | 点击 / 键盘 / 自动 / 信号触发 |
| 触发对象 | 具体节点名或类型 |
| 前置游戏状态 | 在什么 GameState 下可用？ |
| 互斥状态 | 在什么状态下不可用？ |
| 可重复性 | 可重复触发 / 仅一次 / 有冷却 |

**示例**：
- 触发方式：鼠标左键点击
- 触发对象：MountainManager 管理的山峰 Area2D
- 前置状态：GameState.PREPARATION
- 互斥状态：BATTLE / CARD_SELECTION / GAME_OVER
- 可重复性：每座山峰仅修复一次

## 5. 信号契约（新增）

> 模块之间靠信号通信。每个信号要写清楚：谁发射、谁接收、携带什么参数。

```
新信号清单：

信号名（发射者 → 接收者）：signal_name(param1: Type, param2: Type)
  发射者：[模块.文件]
  接收者：[模块.文件]（由 GameManager 在 _ready() 中连线）
  时机：[什么情况下发射]
  参数说明：
    - param1：[类型]，[含义]
```

**示例（山峰修复）**：
```
信号 1（新建）：mountain_repaired(peak_id: String)
  发射者：MountainManager
  接收者：GameManager
  时机：山峰修复成功时
  参数：peak_id — 被修复的山峰 ID

信号 2（复用现有）：mountain_state_changed(peak_id: String)
  发射者：MountainManager
  接收者：GameManager → 转发 → BattleHUD / BattleStartButton
  时机：任何山峰状态变更（修复/升级/选择变化）
```

## 6. 逻辑流程

> 用步骤描述核心逻辑。AI 会据此决定函数拆分。

```
主流程：
  1. [步骤描述] → [涉及的模块/方法]
  2. ...
  3. ...

分支流程：
  - 条件 A 不满足时：[如何处理]
  - 异常情况：[如何处理]
```

**示例**：
```
主流程：
  1. 玩家点击山峰 → MountainManager.try_select_peak_at_point() 判断命中
  2. 命中未修复山峰 → MountainManager 发射 repair_prompt_requested 信号
  3. GameManager 接收信号 → 显示 RepairPromptPanel，传入山峰状态
  4. 玩家点击"修复" → RepairPromptPanel 发射 confirm_repair 信号
  5. GameManager 接收 → 检查灵气是否足够
     - 足够 → MountainManager.repair(peak_id)，灵气扣除
     - 不够 → 按钮保持 disabled

分支：
  - 点击的是已修复山峰 → 直接显示功法选择面板（不经过修复流程）
  - 灵气刚好等于消耗 → 允许修复，修复后灵气=0
```

## 8. 边界条件与互斥

> 把每种"不该发生但可能发生"的情况写清楚。

```
□ 能重复操作吗？不能的话怎么阻止？
□ 有数值上下限吗？
□ 和其他功能互斥吗？
□ 数据不够时：禁用按钮 / 弹窗提示 / 静默失败？
□ 极端值处理：0、负数、空字符串、null？
□ 快速连续点击会怎样？
□ 操作中途切换状态（如从经营进入战斗）会怎样？
```

## 9. 三层归属自查（新增）

> 确认这个功能的新代码不会跨层污染。

```
表现层（新增）：
  - [文件]：[职责]

逻辑层（新增/修改）：
  - [文件]：[职责]

数据层（新增/修改）：
  - [文件]：[职责]

跨层检查：
  □ 表现层代码是否直接读了 CSV？          → 应该通过 DataManager
  □ 逻辑层代码是否直接操作了 UI 节点？     → 应该发射信号
  □ 数据层代码是否发射了信号给 UI？        → 数据层不应知道 UI 存在
```

## 11. 验收标准

> 逐条用"操作 → 预期结果"格式。每条都能用 yes/no 判断。

```
1. [操作] → [预期结果]
2. ...
```

**示例**：
1. 灵气=30，点击未修复山峰 → 弹出修复面板，"修复"按钮可点击
2. 点击"修复" → 灵气变为 10，山峰变亮，面板隐藏修复按钮
3. 灵气=0，点击另一座未修复山峰 → 面板显示，"修复"按钮置灰
4. 战斗中点击山峰 → 无反应（不弹面板）
