## 三、S 级问题（可导致数据损坏或运行异常）

### S1. 上帝 Manager — game_manager.gd (495行)

当前 GameManager 同时承担：状态机、灵气经济、战斗流程、波次桥接、EXP/升级、卡牌触发、输入处理、UI 可见性控制、倒计时动画、山峰操作代理、调试快捷键。

**建议**：拆分为 4 个模块
- `EconomyManager` — 灵气/EXP 经济
- `BattleFlowController` — 战斗流程编排（倒计时→开始→结束→结算）
- `UIStateCoordinator` — UI 状态机（显隐控制、信号驱动）
- `GameManager` — 顶层编排 + 信号中继（~100行）

### S2. 器灵 Profile 数据硬编码 — game_manager.gd:378-394

`_on_start_game_requested()` 中 `spirit_bonus=0.6`、`damage_bonus=0.2`、`exp_bonus=0.4`、`max_hp+=200` 等全部写死在代码中。应新建 `data/spirit_profile_config.csv`，经 DataManager 加载。

### S3. FormConfig Resource 永久污染 — main_peak.gd:131-134

`range_up` 卡牌直接修改 `cfg.range *= (1.0 + effect_value)`，`hp_up` 卡牌直接修改 `max_hp *= (1.0 + effect_value)`。FormConfig 是共享 Resource，变异会跨局残留。

**建议**：`range` 和 `max_hp` 的运行时修改应存储在 channel Dictionary 中的 multiplier 字段，不修改原始 Resource。

### S4. 跨层直接方法调用 — 7 处违反信号契约

| 位置 | 违规 |
|------|------|
| `wave_manager.gd:137` | `get_node(NODE_GAME_MANAGER).add_exp()` |
| `card_manager.gd:72` | `get_node(NODE_MAIN_PEAK).apply_upgrade()` |
| `card_manager.gd:85` | `get_node(NODE_MOUNTAIN_MANAGER).get_all_activated_form_ids()` |
| `mountain_manager.gd:197,255,283` | `_game_manager.try_spend_spirit()` / `on_selected_mountain_changed()` |
| `repair_prompt_panel.gd:244,250` | `gm.repair_selected_mountain()` / `upgrade_selected_mountain()` |
| `result_panel.gd:85` | `gm.return_to_preparation()` |
| `enemy_base.gd:115` | `main_peak.take_damage()` |

**建议**：全部改为信号 — 发射方 emit，GameManager 在 `_ready()` 中 connect 处理。

## 四、A 级问题（功能缺失或设计偏差）

### A1. 山峰升级纯摆设 — mountain_manager.gd:251-262

`upgrade_selected()` 只改 level 计数器，主战斗逻辑 `main_peak.gd:_perform_projectile_attack()` 的伤害公式 `config.damage * channel["damage_multiplier"]` 从未引用 peak level。玩家花灵气升级后战斗数值完全不变。

**建议**：伤害公式改为 `config.damage * channel["damage_multiplier"] * (1.0 + (level - 1) * 0.1)`。

### A2. 防御机制全链路未实装

`form_config.csv` 有 `defense_type`（shield/evasion/lifesteal/block）和 `defense_value` 字段，`card_config.csv` 有 `shield_boost` 卡牌，但战斗中无任何代码检查 `defense_type` 或应用 `defense_value`。

### A3. `speed_up` 卡牌名不副实 — main_peak.gd:127-128

```
"speed_up":
    channel["damage_multiplier"] += effect_value * 0.5
```

描述说"攻击速度 +15%"，实际加的是 `damage_multiplier +7.5%`。`attack_interval` 字段从未被卡牌修改。

### A4. UI 构建函数严重超标

3 个 `_build*()` 函数超 100 行（`main_peak_select_panel.gd:113`、`repair_prompt_panel.gd:110`、`card_selection_panel.gd:99`），且无拆分。应提取 `_build_overlay()`、`_build_card_slot()`、`_build_button()` 等子函数。

### A5. 游戏数据混入 UI — main_peak_select_panel.gd:6-25

`OPTIONS` 数组包含 3 个器灵 Profile 的 id/name/desc/icon，应在 CSV 中定义。

### A6. 元数据滥用 — summon_*.gd

`summon_artfact_sword.gd` 和 `summon_fox.gd` 所有属性通过 `get_meta`/`set_meta` 读写（hp/atk/speed/orbit 等），无任何 typed property。应改用 `@export var`。

### A7. 缺少 `from_csv_row()` 工厂方法

全部 8 个 Resource 类将 CSV→Resource 映射逻辑集中在 `data_manager.gd` 的 5 个 `_load_*()` 方法中（约 80 行）。建议每个 Resource 类增加 `static func from_csv_row(row: Dictionary)`。

### A8. 调试快捷键无守卫 — game_manager.gd:461-468

F1/F2/F3 调试快捷键在发布版本中仍然生效。应包裹 `if OS.is_debug_build():`。
