# 04-质量体系 / 02-评审标准

> **用途**：对代码和设计进行系统性评审时的评分标准。用于架构审查和里程碑复盘。

---

## 一、代码评审维度

### 1. 正确性（权重：40%）
> 代码是否做了该做的事，且只做该做的事？

| 分数 | 标准 |
|------|------|
| 5 | 功能完全符合需求，所有边界条件正确处理，无已知bug |
| 4 | 功能符合需求，个别极端边界未处理但概率极低 |
| 3 | 核心功能正常，1-2个非关键边界未处理 |
| 2 | 核心功能有缺陷，或处理了错误的逻辑 |
| 1 | 功能不可用，或会产生错误结果 |

### 2. 可读性（权重：20%）
> 另一个开发者（或3天后的你）能否在5分钟内理解这段代码？

| 分数 | 标准 |
|------|------|
| 5 | 变量/函数命名自解释，逻辑清晰，无需注释就能理解 |
| 4 | 命名基本清晰，关键逻辑有简要注释 |
| 3 | 能看懂，但部分命名模糊，需要一些猜测 |
| 2 | 多处命名含义不明，逻辑跳跃 |
| 1 | 无法理解，需要重写 |

### 3. 架构一致性（权重：20%）
> 代码是否符合项目既定的架构规范？

| 分数 | 标准 |
|------|------|
| 5 | 完全符合三层架构、模块标准、信号优先原则 |
| 4 | 符合核心架构原则，个别次要规则略有偏差 |
| 3 | 大体符合，但有一个明显的架构违规（如硬编码路径） |
| 2 | 多处违反架构规范 |
| 1 | 完全无视架构规范（如把所有逻辑写在一个文件里） |

### 4. 性能（权重：10%）
> 代码是否在合理时间内完成？是否有明显浪费？

| 分数 | 标准 |
|------|------|
| 5 | 算法复杂度合理，无不必要的 `_process` 计算 |
| 4 | 整体OK，有个别可优化但影响不大的点 |
| 3 | 存在明显可优化的循环或重复计算 |
| 2 | 性能问题可能影响游戏帧率 |
| 1 | 已知的性能瓶颈，需要重构 |

### 5. 安全性（权重：10%）
> 代码是否会崩溃？是否有空指针/越界/类型错误风险？

| 分数 | 标准 |
|------|------|
| 5 | 所有潜在崩溃点有防护（`is_instance_valid`、边界检查、null处理） |
| 4 | 核心路径安全，个别分支可能缺少防护 |
| 3 | 缺少一些防护但不会导致崩溃（结果不正确但不会闪退） |
| 2 | 存在可复现的崩溃风险 |
| 1 | 频繁崩溃 |

## 二、设计评审维度

### 1. 符合 GDD（权重：35%）
> 设计是否与游戏设计文档的定位一致？

| 分数 | 标准 |
|------|------|
| 5 | 完美契合 GDD 定位，强化了核心体验 |
| 4 | 符合 GDD，没有冲突 |
| 3 | 基本符合，但有一个点与 GDD 精神不太一致 |
| 2 | 与 GDD 有明显偏差 |
| 1 | 完全违背 GDD 方向 |

### 2. 数值合理性（权重：25%）
> 数值是否在合理范围内？成长曲线是否平滑？

| 分数 | 标准 |
|------|------|
| 5 | 数值经过验证，成长曲线平滑，与其他功法的数值定位协调 |
| 4 | 数值合理，无明显异常值 |
| 3 | 大致合理，个别数值可能需要调整 |
| 2 | 数值有明显问题（如某级提升过大、与其他功法差距悬殊） |
| 1 | 数值设计有根本性缺陷 |

### 3. 体验连贯性（权重：25%）
> 玩家使用时的感受是否流畅、符合直觉？

| 分数 | 标准 |
|------|------|
| 5 | 操作流畅，反馈清晰，学习曲线自然 |
| 4 | 整体流畅，个别反馈可增强 |
| 3 | 可用但有些别扭（需要额外的说明才能理解） |
| 2 | 体验有明显断点或困惑 |
| 1 | 玩家会觉得这是bug而非设计 |

### 4. 可扩展性（权重：15%）
> 设计是否为未来扩展留有余地？

| 分数 | 标准 |
|------|------|
| 5 | 数据驱动设计，新增内容只需改CSV，不改代码 |
| 4 | 大部分可扩展，部分需要少量代码调整 |
| 3 | 扩展需要中等代码修改 |
| 2 | 硬编码较多，扩展困难 |
| 1 | 完全封闭，无法扩展 |

---

## 三、综合评分

| 总分 | 等级 | 含义 |
|------|------|------|
| 4.5 - 5.0 | 🟢 优秀 | 无需修改，直接通过 |
| 3.5 - 4.4 | 🟡 良好 | 有小问题但可以后续修复，通过 |
| 2.5 - 3.4 | 🟠 需要改进 | 有需要修复的问题，修复后重新评审 |
| 1.0 - 2.4 | 🔴 不合格 | 有根本性问题，需要重新设计/重构 |

### 代码综合分 = 正确性×0.4 + 可读性×0.2 + 架构一致性×0.2 + 性能×0.1 + 安全性×0.1

### 设计综合分 = 符合GDD×0.35 + 数值合理性×0.25 + 体验连贯性×0.25 + 可扩展性×0.15

---

## 四、使用场景

| 场景 | 评审类型 | 评审人 |
|------|----------|--------|
| 新功能架构设计 | 代码评审（侧重架构一致性） | AI自评 + 人类确认 |
| 功能完成后 | 代码评审（全部维度） + 设计评审 | AI自评，人类抽查 |
| 里程碑复盘 | 设计评审（侧重体验和数值） | 人类主导，AI提供数据 |
| 重构前后 | 代码评审（侧重可读性和安全性） | AI自评 |
