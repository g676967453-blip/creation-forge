## 坑 #1: `projects --json` 返回空但网页端有项目

**发现日期**：2026-07-21

**现象**：
```bash
python3 agent_skill.py projects --json
# 返回: { "active": null, "projects": {} }
```
但用户在 https://www.lovart.ai/canvas 上明明有项目。

**原因**：未确认。可能原因：
- AK/SK 关联的账户与网页登录不是同一个
- 项目的 owner 权限与 API Key 的 scope 不匹配
- 后端 API 的环境与前端不同

**规避方法**：
1. 用户在 Lovart 网页端打开项目，从 URL 复制 projectId
2. 手动添加：`python3 agent_skill.py project-add --project-id "xxx" --name "名称"`
3. 添加后一切命令正常工作

**影响范围**：首次配置时。一旦 project-add 完成，后续不再受影响。

## 坑 #2: Windows 上 `/tmp/` 路径用户无法访问

**发现日期**：2026-07-21

**现象**：
```bash
python3 agent_skill.py chat --prompt "..." --json --download
# downloaded[].local_path = "/tmp/openclaw/lovart_01.png"
```
用户（Windows 11）找不到 `/tmp/openclaw/lovart_01.png`。

**原因**：`/tmp/` 在 Git Bash 中映射到 `C:\Users\admin\AppData\Local\Temp\`，但：
1. 用户不一定知道这个映射
2. Git Bash 的 `/tmp/` 和 Windows 的 `%TEMP%` 可能不是同一个
3. 默认 `--output-dir` 使用 Python 的 `tempfile.gettempdir()`，在 Windows 上行为与 macOS/Linux 不同

**规避方法**：
- **始终使用 `--output-dir` 参数**，指定到项目目录
- 或生成后用 `download` 命令单独下载到指定目录：

```bash
python3 agent_skill.py download \
  --urls "https://a.lovart.ai/artifacts/agent/xxx.png" \
  --output-dir "j:/ceshi/projects/asset-pipeline/outputs/GAME-002/portraits" \
  --prefix "GAME-002_portrait_sword-master_bust"
```

**推荐**：未来在 CLAUDE.md 中约定，所有 `chat` 命令带 `--output-dir` 直接指向 `outputs/` 对应目录。

## 坑 #3: 中文路径导致文件操作失败

**发现日期**：2026-07-21

**现象**：
```bash
python3 agent_skill.py download --urls "..." --output-dir "j:/ceshi/projects/GAME-002/美术制作"
# 返回: output_dir: "j:/ceshi/projects/GAME-002/��������"
# 文件未写入正确位置
```

**原因**：Python subprocess / Git Bash / Windows 之间的编码不一致。`美術制作` 中的中文字符在不同编码层之间传递时被破坏。

**规避方法**：
- **所有文件路径使用纯英文**（目录名、文件名）
- 游戏项目目录中的中文名用英文替代（如 `art-assets/` 替代 `美术制作/`）
- 如果必须用中文，在文件系统层面手动管理，不让 Python 脚本接触中文路径

## 坑 #4: Lovart Canvas 浏览器编辑与 API 写入冲突

**发现日期**：2026-07-14（来自 GAME-002 协作日志）

**现象**：用户在 Lovart 网页端打开了项目 Canvas，同时 Claude 通过 API 生成资产。浏览器的自动保存可能覆盖 API 插入的画布元素。

**原因**：Lovart Canvas 的多端编辑没有实时同步锁定机制。

**规避方法**：
- 生成前提醒用户关闭浏览器中的 Lovart 项目页面
- 生成完成后再重新打开
- 图库 (Gallery) 中的图片不受影响——只是 Canvas 布局可能冲突

## 坑 #5: `final_status = "pending_confirmation"` 需要人类确认

**发现日期**：尚未触发，来自 SKILL.md 规则

**现象**：高成本操作（如视频生成）返回 `final_status: "pending_confirmation"`，需要用户确认后才继续。

**Claude 的正确行为**：
1. 显示预估费用给用户
2. **等待用户明确说 yes/确认/搞**

4. 用户拒绝则告知已取消

**Claude 的错误行为**：
- 自动确认（用户没同意就执行 confirm）
- 忽略 pending_confirmation 状态

## 坑 #6: 同一 Prompt 在不同模型上效果差异巨大

**发现日期**：已知（来自 AI 模型通用特性）

**现象**：在 Nano Banana Pro 上效果不错的 Prompt，在 Midjourney 上可能完全不同（反之亦然）。

**原因**：不同模型的训练数据、理解方式、风格偏好不同。

**规避方法**：
- Phase 1 (草稿) 和 Phase 2 (成品) 的 Prompt 可以不同
- Phase 1 用精简关键词（Nano Banana 偏好简洁）
- Phase 2 用完整描述句（Midjourney 偏好自然语言）
- 不要在模型之间对比同一 Prompt 的效果——没有意义

## 坑 #8: 云端项目被删除 → 直连被重置 → 必须走代理

**发现日期**：2026-08-14

**现象**（三层叠加）：
1. `chat` 报 `Error: Project 'xxx' does not exist` —— 本地 state.json 里项目还在，但云端项目已被删除（可能网页端清理过）
2. `create-project` 报 `WinError 10054 远程主机强制关闭连接` —— 直连 `lgw.lovart.ai` 被重置
3. 走本地代理 `127.0.0.1:7897` 后一切正常

**原因**：`projects --json` 只读本地 state，发现不了云端删除；Python urllib 不读 Windows 系统代理，直连不稳时没有任何回退。

**规避方法**：
```bash
export HTTPS_PROXY=http://127.0.0.1:7897 HTTP_PROXY=http://127.0.0.1:7897
# 再执行任意 agent_skill.py 命令
```

**影响范围**：所有 Lovart API 调用。直连时好时坏（昨天批次直连成功，今天重置），**每次跑批都显式 export 代理最稳**。

## 坑 #9: 中文提示词被 Lovart 转译污染

**现象**：中文提示词经 Lovart agent 翻译成英文后语义漂移（细节丢失/风格偏离），同一主题多轮生成不可复现。

**原因**：Lovart agent 层有中→英翻译环节，并非原样传递。

**规避方法**：**英文直写 + 中文包装指令**。提示词主体自己写英文，加一行包装要求原样传递：

```
请直接用下面的英文规格生成 N 张角色原画，每行规格生成一张图，不要改写每行规格内容，原样传递给图片模型。共享画风前缀：{style}
```

已验证 6+ 轮零漂移。详见 [09-角色原画工作流](09-角色原画工作流.md)。

## 坑 #10: 裸头身短语「X heads tall」对图片模型无效

**现象**：批量 100 张提示词带 `3-4.5 heads tall`，agent 实测 2.0~8.5 头身，1/9 达标——参数表锁了，画面没锁。

**原因**：图片模型把「heads tall」当风格提示而非硬约束；不同模型×风格有各自的「风格引力」（风格化3D 的 `toy-like` 拉向 Q 版，MJ 默认写实）。

**规避方法**（三轮校准后）：
1. 用**分数锚点句**：`head height equals one quarter of full body height`（客观比例 > 头身数字）
2. **按模型×风格校准**：过Q组删 `toy-like` + 加 `not chibi` 负向；写实组加 `big head small body` 拉力
3. **适配矩阵兜底**：MJ×3D、GPT2×3D（钟摆震荡）、MJ×韩（无视指令）三个组合对比例**不可控，生产禁用**；韩系/欧美卡通 × GPT2/NBP 5 组合稳定达标
4. **v7 补充：比例句是模型×风格的二元函数**——同是欧美卡通，MJ 拉长用压缩句、gpt2 反而 Q 化（_COMPRESS 全压 2.5），需写目标值 -0.5 补偿。**同风格他模型的校准不可沿用，必须按组合逐一实测**

完整三轮校准数据见 [09-角色原画工作流](09-角色原画工作流.md)。

## 坑 #11: 批量续跑重命名错位

**现象**：组续跑（同线程二次 chat）后 `rename` 把历史产物重命名到新行上，行-图错位。

**原因**：result 返回该线程**全部**历史 artifacts，非只返回新增。

**规避方法**：rename 助手只认 `downloaded[].new == true` 的新文件；超规格产物跳过并清理 hash 残留文件。另注意 timeout ≠ 失败——多数组 timeout 时产物已齐，先轮询 `result --thread-id` 补收，不要重发 prompt。

## 坑 #12: 批量产物顺序与规格行不一致

**现象**：一次 10 行规格的 chat，产物在 result 里的顺序 ≠ prompt 行顺序。按序号直接重命名 → 行-图错位（agent 复核时 faction/corr 全对不上）。

**原因**：agent 并行生成，artifacts 按完成先后返回，不保证与规格行一一对应。

**规避方法**：重命名后必须复核。两种映射手段：① agent 汇总表（agent 回复里常带 corr%+头身+URL 的对照表，按表映射）；② 无法映射时优先信续跑批（同线程二次 chat 的产物顺序通常连续）。最终靠 agent 逐张核对 faction+corr+职业 三要素落盘。

## 坑 #13: 遗留同名文件导致 Windows 重命名崩溃

**现象**：新批次沿用旧批次文件名（同 b 编号同后缀），`Path.rename` 撞已存在文件 → `FileExistsError`，且 rename 助手吞掉异常后静默返回 0 张，排查半天才发现是撞名。

**原因**：重建批次（换风格/换句式重跑）时文件名规则不变，旧文件还在目录里。

**规避方法**：重建批次前先把旧批次归档（如 `west-v1-archive/`、`_stale-archive/`），保证目标目录无同名文件；rename 助手加异常日志而非静默吞掉。

## 坑 #14: Prompt 模板漏拼变量（class_desc 只进文件名）

**现象**：20 小样里 14 张无职业道具（武器/旗枪/卷轴），而文件名里职业是对的——检查才发现 mini_prompt 从没拼过 class_desc。

**原因**：变量在命名规则里、不在提示词模板里；两者分开维护，漏改静默发生，生成端完全察觉不到。

**规避方法**：模板变量表与命名规则同源（都从配置 dict 取），改一处生效两处；批量首轮必做 agent 三要素抽检（faction/corr/职业），不达标就查模板而非怪模型。
