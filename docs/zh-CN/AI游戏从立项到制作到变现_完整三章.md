# 第一章 立项

> 先把方向定义清楚，再交给 AI 加速。

本章回答 8 个立项问题：

1. 为什么 AI 时代立项要更谨慎？
2. AI 改变了哪些立项条件？
3. IAA 用户有什么特点？
4. 应该选择什么产品路线？
5. 什么样的项目适合 IAA？
6. 首版应该验证什么？
7. 立项最容易踩哪些坑？
8. 立项完成后应该输出什么？

核心目标：**把模糊想法，收敛成可执行的验证方案。**

---

## 1.1 AI 提高的是执行效率，不是方向准确率

方向不准确，AI 执行得越快，亏损累积越快。

常见风险：

- 错误方向被快速做完整
- 高完成度带来虚假信心
- 核心未验证就扩大投入

> 方向越偏，亏损越快；反馈目标不清，就不知道下一步改什么；反复返工还会持续消耗团队信心。

---

## 1.2 AI 时代立项，先判断团队能否驾驭四个变量

| 过去 | AI 时代 |
| --- | --- |
| 做不出来 | 做得快，更要管得住 |
| 程序资源不足 | Token：每次生成与返工都在计费 |
| 美术成本太高 | 工作流：需求、验收、反馈必须前置 |
| 内容生产太慢 | 速度：判断节奏必须跟上生产节奏 |
| 研发周期太长 | 团队基因：判断与审美决定产出上限 |

> AI 决定团队能做多快，治理能力决定项目能不能做对。

---

## 1.3 IAA 用户不是一类固定人群，而是一种低承诺的游戏状态

特征：

- 被素材触发
- 进入耐心短
- 碎片化游玩
- 选择多、流失快

关键词：非主动搜索、低学习耐心、随时可退出、选择多迁移快。

这些特点决定四条立项方向：

1. 入口必须直观
2. 反馈必须及时
3. 核心循环短且可重复
4. 题材与操作足够广谱

---

## 1.4 短期爆款，还是轻度长线，内容承诺完全不同

### 微信 / 抖音短期爆款

- 代表：《羊了个羊》、铲树皮类
- 特点：单一爽点 · 解压传播 · 快速爆发

### 轻度长线 / 内容经营

- 代表：《幸福路上的火锅店》《消灭病毒》《网吧模拟器》
- 特点：重数值 · 内容丰富 · 长短期目标明确

---

## 1.5 适合 IAA 的五项判断标准

五项都成立，才值得进入原型验证：

| 标准 | 含义 | 重要性 |
| --- | --- | --- |
| 素材可表达 | 一张图或 3 秒视频说明核心吸引力 | 必要 |
| 操作可进入 | 单手、单指、无需复杂教程 | 必要 |
| 爽点可重复 | 反馈来得快，重复体验仍然成立 | 核心 |
| 内容可扩展 | 规则不变，关卡能持续组合 | 必要 |
| 商业可承载 | 复活、加倍、奖励都有价值交换 | 必要 |

> 判断原则：不做少部分人强烈喜欢的高门槛体验，做大部分人不讨厌、愿意试一次的体验。

---

## 1.6 立项必须先定义验证范围，而不是直接定义完整产品

进入制作前，先把一个想法压缩成可验证的首版：

- **核心假设**
  - 首版证明什么
  - 唯一关键问题：用户为什么继续
  - 核心爽点是否成立
- **原型范围**
  - 只做最小闭环
  - 一个核心循环
  - 最低必要美术
  - 明确暂时不做
- **验证边界**
  - 提前定义标准
  - 需要什么反馈
  - 时间与 Token 上限
  - 谁负责最终验收

> 没有反馈标准，AI 生成得越多，团队越不知道下一步该改什么。

---

## 1.7 立项最常见的错误

1. **把"AI 能生成"当成"用户会需要"** —— 生产能力不能替代用户需求。
2. **看到热点玩法就直接复制** —— 没有理解它为什么成立。
3. **用系统、美术和内容掩盖核心问题** —— 核心不成立，堆内容没有意义。
4. **同时验证多个方向和变量** —— 无法判断反馈究竟来自哪里。

> 先验证核心，再扩展内容；一次只验证一个关键假设。

---

## 1.8 立项的交付物

一份可以直接进入制作的验证方案，包括：

1. **项目定义**：为谁做、满足什么需求
2. **核心体验**：玩什么、爽点在哪里
3. **产品路线**：超休闲验证或长期经营
4. **验证方案**：首版范围、反馈与资源上限

进入制作前必须达成一致：

- 方向达成一致
- 范围达成一致
- 标准达成一致

> 立项阶段不决定项目最终生死，只决定先验证什么，以及用多少成本验证。

用户清楚 · 核心明确 · 路线一致 · 范围可控 · 反馈可判断 · 成本有上限

---

## 1.9 第一章总结

立项先把四件事说清楚：

1. **先定用户**：面向广谱 IAA 用户，不追求少部分人特别喜欢，而是让大部分人不讨厌。
2. **再定路线**：短期爆款依赖单一爽点与传播；长线产品依赖重数值、丰富内容和明确的长短期目标。
3. **再定项目**：核心玩法必须低门槛、强反馈、可重复，同时具备清晰的素材表达和商业化空间。
4. **最后定边界**：明确首版做什么、不做什么、验证什么，以及最多投入多少成本。

> AI 可以加速制作，但只有用户、路线、项目和边界清晰，才值得进入制作。

# 第二章 制作

> 把策划、美术、代码与内容组织成稳定生产线。

本章回答 8 个制作问题：

1. 一款游戏完整的制作流程是什么？
2. 策划怎样转成可执行的制作方案？
3. 为什么先定美术主题再批量生产？
4. 工程代码应该按照什么顺序搭建？
5. 内容和数值如何进入配置工作流？
6. 整合与 QA 怎样形成修复闭环？
7. 各阶段应该选择哪些平台？
8. 怎样搭建可交接、可恢复的工作流？

核心观点：**AI 制作的关键，不是生成得多，而是生产链能够稳定交接。**

---

## 2.1 游戏制作不是一次生成，而是五个阶段依次交接

| 阶段 | 关键产出 | 推荐平台 |
| --- | --- | --- |
| 策划流程 | 设计文档 · 功能清单 · SOP | SeaGamePlay |
| 美术主题 | 风格指南 · 样张 · 资产规范 | SeaGamePlay |
| 工程代码 | 可运行工程 · 核心闭环 | SeaGamePlay |
| 内容数值 | 配置表 · 关卡 · 成长曲线 | SeaGamePlay |
| 整合与 QA | 测试报告 · 发布候选版本 | SeaGamePlay |

> 一站式路线用 SeaGamePlay 贯穿全流程；组合路线自行选择工具并完成阶段交接。

---

## 2.2 策划不是写一份文档，而是建立后续制作的共同标准

把立项结论转成规则、功能、页面、优先级和验收标准。

关键输出：

- 核心循环
- 功能清单
- 首版范围
- 验收标准

两条路线：SeaGamePlay ｜ 对话 AI + 飞书

流程：

1. 立项结论进入策划
2. AI 生成策划初稿
3. 制作人审核与删减
4. 冻结策划基线并交接

---

## 2.3 IAA 美术不只是好看，而是让玩家一眼看懂并愿意点开

美术优先级：

1. 画面能看懂玩法目标
2. 操作对象与反馈足够突出
3. 题材、角色和色彩符合泛用户审美
4. 不用阅读文字，也能理解核心爽点

> 判断标准：大部分人不一定喜欢，但不能让大部分人反感。

---

## 2.4 组合路线的美术环节

SeaGamePlay 可一站式完成；选择工具组合时，再按阶段选择美术平台与模型。

### 快速探索

- 目标：快速确定题材与视觉方向
- 平台：SeaGame 美术 · 海艺 SeaArt · 即梦
- 模型：Seedream · GPT Image · Nano Banana 2 Pro
- 输出：3—5 套主题样张

### 批量资产

- 目标：稳定生成角色、场景与 UI
- 平台：SeaGame 美术 · ComfyUI
- 重点：尺寸、命名、透明底与规格统一
- 输出：规格化正式资产

### 风格固化

- 目标：让同一项目长期保持一致
- 平台：SeaGame 美术
- 重点：角色、色彩、材质与镜头语言不跑偏
- 输出：风格基线、资产模板与版本记录

> 一站式路线用 SeaGamePlay；组合路线用 SeaGame 美术生产专业资产，外部平台按需补充。

---

## 2.5 工程平台有两条路线

### 一站式方案：SeaGamePlay

- 多模态一站式构建
- 策划、美术、工程、内容、QA 同一平台
- 无需再组合其他生产平台

### 组合方案：执行 Agent + IDE 协作

- 执行 Agent：Codex / Claude Code
  - 读工程、改多文件、运行命令与测试
  - 适合功能开发、Bug 修复、重构
  - 要求搭配版本管理、测试与验收
- IDE 协作：Cursor
  - 工程内理解、局部修改、Diff 审查
  - 适合人工与 Agent 共同开发
  - 要求搭配任务管理、测试与版本控制

> 两条路线：SeaGamePlay 一站式 ｜ 或 Codex / Claude Code + Cursor 工具组合。

---

## 2.6 无论选哪条路线，工程任务都要进入受控工作流

流程：

1. **任务输入**：需求、资产、配置与工程基线
2. **建立工作包**：指定 Agent、授权模块、禁止修改区
3. **Agent 执行**：读 Index → 局部修改 → 自测 → 输出 Diff
4. **验收合并**：预览、测试、代码审查、回收稳定版本

每轮必须产出：

- 可运行版本
- 变更 Diff
- 测试结果

> 工作包未明确目标平台、授权范围和验收标准，就不允许 Agent 开始写代码。

任务入口 → WorkPackage → Agent 执行 → 预览 / 测试 → 验收 → Git 合并

---

## 2.7 AI 写代码最怕"大力出奇迹"

注意事项要盯住三件事：代码膨胀、模块耦合和版本失控。

### STEP 01 防止代码膨胀

- 禁止重复实现同一能力
- 无用脚本与废弃分支及时删除
- 优先复用已有组件和接口

### STEP 02 防止模块耦合

- 业务、UI、数据分层
- 公共能力只保留一个入口
- 禁止任务跨模块顺手乱改

### STEP 03 保证版本可恢复

- 每个任务独立分支
- 每次提交都能运行
- 出现偏差立即回退

> 工程红线：不堆代码 · 不重复造轮子 · 不跨模块乱改 · 不允许 Agent 整工程重写。

---

## 2.8 内容与数值必须进入配置工作流，而不是写死在代码里

| 步骤 | 内容 | 工具 |
| --- | --- | --- |
| 配置结构 | 关卡、奖励、成长字段先定义 | 配置工具 |
| 基础数值 | 首批内容只覆盖一段完整体验 | Excel |
| 游戏内验证 | 验证难度、节奏、产出与消耗 | Cocos |
| 批量扩展 | 关卡、资产和配置按模板生成 | 资产工具 |
| 版本锁定 | 记录修改原因、版本和影响范围 | Git |

> 短期产品强化爽点与重复；长线产品建立重数值、丰富内容和明确的长短期目标。

---

## 2.9 QA 不是最后玩一遍，而是定位、修复、回归的闭环

1. **先整合，再建立候选版本**：代码、资产、配置和平台包必须来自同一版本
2. **自动冒烟 + 人工完整体验**：功能、异常、边界、存档和完整流程同时覆盖
3. **Bug 分类后交回责任模块**：脚本、资产、配置、性能和平台问题分别处理
4. **局部修复后必须回归**：确认问题消失，并验证没有破坏其他模块

平台：

- 一站式：SeaGamePlay
- 组合：Cocos Profiler · Chrome DevTools · 微信/抖音开发者工具 · Playwright

---

## 2.10 第二章总结

AI 制作要建立稳定生产线：

1. **先定标准，再开始生产**：策划、美术与工程基线先明确，下游才不会反复返工。
2. **先跑闭环，再扩大内容**：工程先可玩，内容和资产再批量扩展。
3. **任务有边界，AI 才能稳定执行**：明确输入、修改范围与输出，避免无效生成和跨模块乱改。
4. **每个阶段都要可验收、可恢复**：整合、测试、回归与版本记录形成完整交付闭环。

> 不要让 AI 做抽象决策；让 AI 负责流程化执行，并用建议推动下一步。

# 第三章 商业化

> 从做产品到做生意，让用户价值、体验与收入形成循环。

本章回答 8 个商业化问题：

1. 从做产品到做生意，判断标准如何改变？
2. 什么产品，应该采用什么回收逻辑？
3. 怎样先设计价值交换，再设计广告？
4. 激励视频、插屏与 Banner 怎样使用？
5. 商业化数据链应该怎样搭建？
6. 什么数据决定继续投入、调整或放弃？
7. 为什么跑通回收之后才能扩大买量？
8. 短期爆款与长线产品怎样区别变现？

核心观点：**商业化不是多塞广告，而是证明每一次追加投入都有回收依据。**

---

## 3.1 产品成立，不是"能上线"，而是关键测试数据同时过线

CPI、首日广告承载、首日变现、3 日与 7 日回收必须共同成立，不能只拿一个好指标证明项目成立。

| 指标 | 关注项 | 及格标准 |
| --- | --- | --- |
| 获客成本 CPI | 素材 CTR · 安装转化 · 渠道质量 | CPI 低于立项预设成本线 |
| 首日广告承载 | 人均广告次数 · 激励完成率 · 插屏触发率 | 广告密度达到模型且不伤体验 |
| 首日变现 | D0 ARPDAU · D0 ROI · 首日 LTV | 短期超休的核心判断闸门 |
| 3 日验证 | D1/D3 留存 · 累计 ROI · ARPDAU 趋势 | 首日收入能否继续延伸 |
| 7 日验证 | D7 留存 · 累计 ROI · LTV 斜率 | 长线产品的早期回收证明 |

> 先写及格线再测试：CPI、首日广告次数、首日 ARPDAU/ROI、D3、D7，任何一项都不能用"感觉不错"代替。

---

## 3.2 短期超休看首日 ROI，轻度长线看 LTV

### 短期超休

- 首日 ROI 优先
- CPI 必须低于预设线
- 首日广告次数与 ARPDAU 达到模型
- D0 ROI 是继续投入的核心闸门
- D3/D7 只确认尾部回收

### 轻度长线

- LTV 优先
- D1/D3/D7 留存必须支持长期回收
- 广告次数与 ARPDAU 不能靠伤留存抬高
- D7 之后的 LTV 斜率仍要继续增长
- 允许首日 ROI 较低，但最终必须覆盖 CPI 与内容成本

> 短期看多久收回，长线看最终能收回多少；两种产品必须使用不同的数据权重和及格线。

---

## 3.3 先设计玩家愿意接受的价值交换，再决定广告放在哪里

价值交换模型：

- **玩家获得明确价值**：奖励 · 复活 · 加速 · 额外内容
- **产品获得商业价值**：展示机会 · 广告收益 · LTV

> 广告前知道能得到什么，广告后立刻兑现。广告不能破坏核心节奏，也不能替代游戏本身的奖励设计。

---

## 3.4 广告形式没有好坏，只有是否放在正确的玩家时刻

先看玩家是否主动、是否中断体验、是否获得对价，再决定广告形式与频次。

主要广告形式：

- 激励视频
- 插屏
- Banner

四条商业化原则：

1. 由玩家主动触发
2. 只放在自然断点
3. 不遮挡核心操作
4. 设置冷却、频控与失败兜底

---

## 3.5 商业化数据不是一组散指标，而是一条投入—回收链

### 投入端：买量与新增

- CPI / CPA：获得一个用户要花多少钱
- 素材点击率、转化率、渠道质量
- 先确认流量不是买得越多亏得越多

### 体验端：留存与广告

- D1 / D3 / D7：用户能留多久
- 展示率、完成率、每 DAU 展示次数
- 判断广告是否建立在真实体验之上

### 回收端：收入与 LTV

- ARPDAU：每天每活跃用户贡献多少
- LTV：生命周期累计贡献多少
- 最终比较：LTV 是否覆盖 CPI 与内容成本

> 核心关系：用户价值 × 留存时长 × 广告效率 = 可回收的 LTV

---

## 3.6 数据不是汇报结果，而是决定继续投入、调整还是放弃

| 决策 | 条件 |
| --- | --- |
| 继续投入 | 留存稳定 · LTV 覆盖成本 · 放量不恶化 |
| 局部调整 | 核心体验成立，但素材、频次或数值仍可修 |
| 缩小验证 | 信号不稳定，降低预算，只验证一个变量 |
| 及时放弃 | 留存与回收同时不成立，且无明确修复假设 |

决策必须写清：

- 依据数据
- 下一假设
- 预算上限

> 没有明确阈值、修复假设和预算上限，就不应该用"再试一下"继续投入。

观察数据 → 对照阈值 → 判断原因 → 继续 / 调整 / 缩小 / 放弃

---

## 3.7 先证明单个用户能回收，再扩大买量与内容投入

放量四步：

1. **小预算验证单用户模型**：确认流量质量、留存与广告收益是否可重复
2. **验证边际放量是否稳定**：预算增加后，CPI、留存和广告效率不能明显恶化
3. **扩大渠道与素材供给**：避免依赖单一素材、单一渠道或偶然流量
4. **扩大内容与团队投入**：只有回收稳定，长线内容成本才有投入依据

> 放量原则：回收先于规模，稳定先于速度；预算放大时，数据必须重新验证。

---

## 3.8 短期爆款与长线产品，商业化节奏不能使用同一套模板

| 维度 | 短期爆款 | 长线产品 |
| --- | --- | --- |
| 新增来源 | 传播爆发、素材快速迭代 | 持续买量与渠道扩展 |
| 广告节奏 | 更早验证、短周期释放收益 | 长期稳定、不伤留存 |
| 内容投入 | 只维护核心爽点与必要变体 | 重数值、丰富内容、持续更新 |
| 回收逻辑 | 短期快回收 | 长线抬高 LTV |
| 投入判断 | 短期看快速回收 | 长线看生命周期回收 |

> 短期产品争取在流量窗口内快速回收；长线产品用留存和内容换取更高 LTV 与更长回收周期。

## 3.9 第三章总结

从做产品，到做成一门可持续的生意：

1. **定路线**：短期快回收 / 长线抬高 LTV
2. **做交换**：让玩家明确得到什么价值
3. **看数据**：预设阈值、假设和预算上限
4. **再放大**：单用户模型成立，再扩大投入

> 商业化不是多放广告，而是找到适合产品的回收方式，让每一次追加投入都有数据依据。

产品路线决定回收逻辑 · 价值交换决定广告体验 · 数据决定投入去留
