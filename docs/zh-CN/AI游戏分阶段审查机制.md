# AI 游戏项目分阶段审查机制

> 配套文档：《AI游戏从立项到制作到变现_完整三章》
> 适用对象：IAA 超休闲 / 轻度游戏项目
> 机制定位：把"方向、标准、验收"前置为门禁，防止 AI 时代"执行快、返工贵、亏损快"

---

## 0. 为什么要建立分阶段审查机制

原文核心观点：**AI 提高的是执行效率，不是方向准确率；方向越偏，亏损越快。**

- 生成与返工都在计费（Token 成本）
- 需求、验收、反馈必须前置（工作流成本）
- 判断节奏必须跟上生产节奏（速度成本）
- 团队基因决定产出上限（治理成本）

因此：**审查不是流程负担，而是控制"做错方向"与"无效返工"成本的手段。**

总原则（原文档 1.8 / 2.2 / 2.10）：

> 进入下一阶段前必须达成一致：方向一致 · 范围一致 · 标准一致。
> 每个阶段都要可验收、可恢复；不要让 AI 做抽象决策，让 AI 做流程化执行，并用建议推动下一步。

---

## 1. 机制总览：三大阶段、七个门禁

| 门禁 | 阶段 | 审查时机 | 核心问题 | 对应原文 |
| --- | --- | --- | --- | --- |
| G0 | 立项 | 进入原型验证之前 | 方向、范围、标准是否清晰 | 第一章 |
| G1 | 制作·策划 | 策划基线冻结前 | 功能、范围、验收标准是否可执行 | 2.2 |
| G2 | 制作·美术 | 批量生产前 | 风格基线、资产规范是否已冻结 | 2.3 / 2.4 |
| G3 | 制作·工程 | 每个工作包合并前 | 是否可运行、有 Diff、通过测试 | 2.5 / 2.6 / 2.7 |
| G4 | 制作·内容与 QA | 发布候选版本前 | 配置受控、回归闭环是否完成 | 2.8 / 2.9 |
| G5 | 商业化·产品成立 | 关键数据齐备时 | 数据是否同时过线 | 3.1 / 3.2 |
| G6 | 商业化·放量 | 扩大投入前 | 单用户模型是否成立、边际是否稳定 | 3.6 / 3.7 |

**流程**：G0 → G1 → G2 → G3 → G4 → 上线 → G5 → G6

> 任何门禁未通过，不允许进入下一阶段；允许退回上游修正，不允许跳关。

## 2. 通用审查规则

### 2.1 每个门禁必须写清三要素
1. **审查清单**：本阶段必须逐项回答的问题（见各节）
2. **通过标准**：明确的、可量化的达标线
3. **否决项**：一票否决的红线

### 2.2 决策规则
- **绿灯**：全部审查项通过 → 放行
- **黄灯**：部分通过，带有修复假设 → 限时修复后复审，**禁止带病进入下一阶段**
- **红灯**：核心项不通过 → 退回修正或放弃，**禁止"先往下做再说"**

### 2.3 一次只验证一个变量
（原文档 1.7）同时验证多个方向或变量时，无法判断反馈来自哪里 → 一律红灯。

### 2.4 审查记录
每次审查输出：审查日期、审查人、逐项结论、遗留项、修复期限、下一门禁时间。
（角色建议：G0/G1/G5/G6 由制作人/项目负责人主持；G3 由技术负责人+制作人；G4 由测试负责人。）

---

## 3. G0 立项审查（进入原型验证前）

### 3.1 审查时机
立项交付物完成后、原型制作开始前。

### 3.2 审查清单

**A. 方向审查（原文档 1.1 / 1.2 / 1.9）**
- [ ] 是否明确"为谁做、满足什么需求"——IAA 用户是一种低承诺状态：素材触发、耐心短、碎片化、随时可退出
- [ ] 团队能否驾驭四个变量：Token 成本、工作流前置、节奏、判断与审美
- [ ] 用户 · 路线 · 项目 · 边界 四件事是否已说清楚

**B. 路线审查（原文档 1.4 / 3.8）**
- [ ] 明确路线：短期爆款（单一爽点、解压传播）还是轻度长线（重数值、内容丰富、长短期目标）
- [ ] 内容承诺与路线匹配

**C. 五项判断标准审查（原文档 1.5）—— 五项全部成立才放行**

| 标准 | 审查问题 | 重要性 |
| --- | --- | --- |
| 素材可表达 | 一张图或 3 秒视频能说明核心吸引力？ | 必要 |
| 操作可进入 | 单手、单指、无需复杂教程？ | 必要 |
| 爽点可重复 | 反馈来得快，重复体验仍成立？ | 核心 |
| 内容可扩展 | 规则不变，关卡能持续组合？ | 必要 |
| 商业可承载 | 复活/加倍/奖励有明确价值交换？ | 必要 |

**D. 验证范围审查（原文档 1.6）**
- [ ] 核心假设：首版证明什么？唯一关键问题"用户为什么继续"？核心爽点是否成立
- [ ] 原型范围：最小闭环、一个核心循环、最低必要美术、"明确暂时不做"清单
- [ ] 验证边界：反馈标准提前定义、时间与 Token 上限、最终验收负责人

**E. 立项错误排查（原文档 1.7）—— 任一命中即红灯**
- [ ] 是否把"AI 能生成"当成"用户会需要"
- [ ] 是否看到热点玩法直接复制而未理解其成立原因
- [ ] 是否用系统、美术、内容掩盖核心问题
- [ ] 是否同时验证多个方向和变量

### 3.3 通过标准（原文档 1.8）
**用户清楚 · 核心明确 · 路线一致 · 范围可控 · 反馈可判断 · 成本有上限**，六项同时成立。

### 3.4 交付物
项目定义、核心体验、产品路线、验证方案（含首版范围、反馈与资源上限）。
> 立项阶段不决定项目最终生死，只决定先验证什么、用多少成本验证。

## 4. 制作阶段审查

### 4.1 G1 策划基线审查

**审查时机**：策划初稿完成后、基线冻结交接前（原文档 2.2 流程第 4 步）

**审查清单**
- [ ] 核心循环已定义
- [ ] 功能清单完整且可排优先级
- [ ] 首版范围明确（做什么 / 不做什么）
- [ ] 验收标准可执行（下游可据此直接验收）
- [ ] 已经过制作人审核与删减（AI 生成初稿 → 人工删减，防止"生成得多 = 做得多"）

**通过标准**：策划基线冻结；**未冻结不允许进入美术 / 工程生产**。
**否决项**：验收标准含糊、范围未删减 → 退回修改。

### 4.2 G2 美术主题与资产审查

**审查时机**
- 快速探索阶段：3—5 套主题样张产出后，确定视觉方向（原文档 2.4）
- 批量生产前：必须先完成风格固化，再批量生成（原文档 2.4）

**审查清单（按原文档 2.3 美术优先级）**
- [ ] 画面能看懂玩法目标（优先级 1）
- [ ] 操作对象与反馈足够突出（优先级 2）
- [ ] 题材、角色、色彩符合泛用户审美（优先级 3）
- [ ] 不用阅读文字也能理解核心爽点（优先级 4）
- [ ] 批量资产规格统一：尺寸、命名、透明底
- [ ] 风格基线、资产模板与版本记录已建立

**通过标准**："大部分人不一定喜欢，但不能让大部分人反感"；风格基线冻结后再批量生产。
**否决项**：未定风格基线就批量生成 → 资产存在作废风险，退回。

### 4.3 G3 工程工作包审查

**审查时机**：每个工作包合并前（原文档 2.6）

**前置条件（缺一不可开工，原文档 2.6）**
- [ ] 工作包明确目标平台
- [ ] 工作包明确授权范围（指定 Agent、授权模块）
- [ ] 工作包明确禁止修改区
- [ ] 工作包明确验收标准

**每轮产出审查**
- [ ] 可运行版本
- [ ] 变更 Diff
- [ ] 测试结果

**工程红线审查（原文档 2.7）—— 任一违反即红灯**
- 代码膨胀：是否重复实现同一能力、无用脚本与废弃分支是否删除、是否优先复用
- 模块耦合：业务/UI/数据是否分层、公共能力是否单入口、是否跨模块顺手乱改
- 版本失控：每任务独立分支、每次提交可运行、出现偏差是否立即回退

**通过标准**：预览、测试、代码审查通过，回收稳定版本后 Git 合并。
**否决项**：整工程重写、跨模块乱改、提交不可运行。

### 4.4 G4 内容数值与 QA 发布审查

**审查时机**：发布候选版本形成前（原文档 2.8 / 2.9）

**内容配置审查**
- [ ] 配置结构先行：关卡、奖励、成长字段先定义，不写死在代码里
- [ ] 首批内容只覆盖一段完整体验（不贪多）
- [ ] 游戏内验证：难度、节奏、产出与消耗符合设计
- [ ] 批量扩展按模板生成
- [ ] 版本锁定：修改原因、版本、影响范围有记录

**QA 闭环审查**
- [ ] 整合审查：代码、资产、配置、平台包来自**同一版本**
- [ ] 自动冒烟 + 人工完整体验（功能、异常、边界、存档、完整流程）
- [ ] Bug 已分类并交回责任模块（脚本 / 资产 / 配置 / 性能 / 平台）
- [ ] 局部修复后完成回归：问题消失 + 未破坏其他模块

**通过标准**：测试报告完成，形成发布候选版本。
**否决项**：非同版本整合、回归未通过。

## 5. 商业化阶段审查

### 5.1 G5 产品成立数据闸门（原文档 3.1 / 3.2）

**审查原则**：产品成立 ≠ 能上线；关键测试数据必须**同时**过线，任何一项不能用"感觉不错"代替。**及格线必须先写再测。**

| 指标 | 审查关注项 | 及格标准（提前定义） |
| --- | --- | --- |
| 获客成本 CPI | 素材 CTR · 安装转化 · 渠道质量 | 低于立项预设成本线 |
| 首日广告承载 | 人均广告次数 · 激励完成率 · 插屏触发率 | 广告密度达标且不伤体验 |
| 首日变现 | D0 ARPDAU · D0 ROI · 首日 LTV | 短期超休的核心判断闸门 |
| 3 日验证 | D1/D3 留存 · 累计 ROI · ARPDAU 趋势 | 首日收入能否继续延伸 |
| 7 日验证 | D7 留存 · 累计 ROI · LTV 斜率 | 长线产品的早期回收证明 |

**路线差异化审查（原文档 3.2）**
- 短期超休：首日 ROI 优先；CPI 低于预设线；D0 ROI 是核心闸门；D3/D7 只确认尾部回收
- 轻度长线：LTV 优先；D1/D3/D7 留存必须支持长期回收；D7 后 LTV 斜率继续增长；允许首日 ROI 较低，但最终必须覆盖 CPI 与内容成本

**广告体验审查（原文档 3.3 / 3.4）**
- [ ] 价值交换成立：玩家获得明确价值（奖励 / 复活 / 加速 / 额外内容）⇄ 产品获得商业价值
- [ ] 广告由玩家主动触发
- [ ] 只放在自然断点
- [ ] 不遮挡核心操作
- [ ] 有冷却、频控与失败兜底

### 5.2 G6 投入决策与放量审查（原文档 3.6 / 3.7）

**数据决策审查**——每个决策必须写清三件事：**依据数据 · 下一假设 · 预算上限**

| 决策 | 放行条件 |
| --- | --- |
| 继续投入 | 留存稳定 · LTV 覆盖成本 · 放量不恶化 |
| 局部调整 | 核心体验成立，素材 / 频次 / 数值仍可修（限时复审） |
| 缩小验证 | 信号不稳定，降低预算，只验证一个变量 |
| 及时放弃 | 留存与回收同时不成立，且无明确修复假设 |

**放量四步审查（按序放行，原文档 3.7）**
1. 小预算验证单用户模型：流量质量、留存、广告收益可重复
2. 验证边际放量稳定：预算增加后 CPI、留存、广告效率不明显恶化
3. 扩大渠道与素材供给：不依赖单一素材、单一渠道或偶然流量
4. 扩大内容与团队投入：回收稳定后，长线内容成本才有投入依据

**否决项**：无阈值、无修复假设、无预算上限就"再试一下"；回收未先于规模。

---

## 6. 横切审查：贯穿全程的两条红线

1. **成本红线**：每个验证阶段预设时间与 Token 上限（原文档 1.6），超支即触发复审
2. **版本红线**：所有阶段产物（文档、资产、代码、配置、平台包）必须可交接、可恢复（原文档 2.10）

## 7. 审查机制速查表

| 门禁 | 时机 | 一票否决项 | 通过标志 |
| --- | --- | --- | --- |
| G0 立项 | 原型验证前 | 五项标准任一不成立 / 多变量并行 / "AI 能生成 ≠ 用户需要" | 六项一致：用户·核心·路线·范围·反馈·成本 |
| G1 策划 | 基线冻结前 | 验收标准含糊 / 范围未删减 | 策划基线冻结并交接 |
| G2 美术 | 批量生产前 | 无风格基线就批量生成 | 风格基线 + 资产规范冻结 |
| G3 工程 | 每个工作包合并前 | 整工程重写 / 跨模块乱改 / 提交不可运行 | 可运行 + Diff + 测试通过并合并 |
| G4 内容与 QA | 发布候选前 | 非同版本整合 / 回归未通过 | 测试报告 + 发布候选版本 |
| G5 产品成立 | 关键数据齐备 | 单指标自证 / 无预写及格线 | 五组数据同时过线 |
| G6 放量 | 扩大投入前 | 无阈值 / 假设 / 预算上限 | 单用户模型成立 + 边际放量稳定 |

---

## 8. 结语

> 让 AI 负责执行，让人负责方向、判断与审美。
> 审查机制的落点不是"卡流程"，而是保证每一步追加投入（时间、Token、买量预算）都有明确的验收依据。
