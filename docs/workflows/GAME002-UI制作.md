# GAME-002 UI 制作

> 版本：v2 | 最后更新：2026-07-22 | 对应 SKILL：待建

## 触发条件

GAME-002「开仙门」功能开发流程中，Step 2（功能规划）完成后，需要将策划文档中的 UI 描述转化为可执行的美术需求。

典型场景：
- 功能规划文档已输出「界面描述」和「美术与体验需求」初稿
- 需要系统性地拆解出：有哪些 UI 界面 → 怎么交互 → 长什么样 → 需要哪些美术资产
- 产出的美术需求将交给 asset-pipeline 生产资产、交给功能开发 Step 5 做引擎实现

## 流程定位

```
策划文档（上游）           本工作流（设计层）            执行层（下游）
──────────────────      ──────────────────      ──────────────────
功能规划文档 §4         策划解读 → UI场景清单
"美术与体验需求"  ──→   交互设计 → 交互需求      ──→  功能需求文档 §7-附
                        视觉设计 → 视觉方向+Pixso ──→  asset-pipeline 资产生成
                        资产拆解 → 美术资产清单   ──→  美术绘制规范 §7 资产清单
                                                      GAME002-功能开发 Step 5
```

> ⚠️ 本工作流是**纯设计阶段**工作流。不涉及 Godot 代码、不查引擎工程、不从已有实现反推。引擎实现由 [GAME002-功能开发](GAME002-功能开发.md) Step 5 负责。

## 流程总览

```
策划解读 → 交互设计 → 视觉设计 → 资产拆解
  (1)        (2)        (3)        (4)
```

## 人机分工

| 阶段 | 人 | AI（Claude） |
|------|-----|-------------|
| 1. 策划解读 | 确认 UI 场景覆盖完整 | 读策划文档，识别所有 UI 界面，输出场景清单 |
| 2. 交互设计 | 逐个界面确认交互逻辑 | 设计状态/交互流/信息架构/异常分支 |
| 3. 视觉设计 | 判断"这种感觉对不对" | 对齐风格体系，描述视觉方向，可出 Pixso 布局 |
| 4. 资产拆解 | 确认优先级和范围 | 逐界面拆解资产，填规格表，A/V/S 编号 |

## 执行步骤

### 阶段 1：策划解读 → UI 场景提取

**目标**：从策划文档中识别所有涉及的 UI 界面，列出清单，确认没有遗漏。

**输入**：功能规划文档（特别是「界面描述」「交互方式」「美术与体验需求」章节）。

**步骤**：

1. AI 读取功能规划文档，逐段标注涉及 UI 的描述
2. 识别每个独立 UI 界面/面板，提炼为结构化条目
3. 识别界面之间的跳转关系（A→B→C，什么事件触发跳转）
4. 输出 UI 场景清单，人类确认覆盖面

**UI 场景清单模板**：

| # | 界面名称 | 用途（一句话） | 触发时机 | 所属游戏状态 | 跳转到 |
|---|---------|-------------|---------|------------|--------|
| 1 | 开场黑幕 | 世界观叙事淡入 | 游戏启动 | INTRO | → 器灵选择 |
| 2 | 器灵选择面板 | 选择初始器灵 | 开场结束 | MAIN_PEAK_SELECT | → 经营界面 |

**产出**：UI 场景清单表，追加到策划文档或独立保存。

**判断标准**：人类看完能确认"所有界面都列出来了，没有遗漏"。

---

### 阶段 2：交互设计 → 状态 + 流程

**目标**：把每个 UI 界面的交互逻辑说清楚——什么状态下显示什么、用户能做什么、系统怎么响应。

**输入**：UI 场景清单 + 策划文档中的交互描述。

**步骤**：

1. **状态定义**：对每个界面，列出所有可能的状态：
   - 正常态、空状态、禁用态、悬停态、加载态、错误态、动画过渡态
   - 标注每个状态下哪些元素可见、哪些隐藏
2. **交互流程**：
   - 用户操作（点击/拖拽/键盘/滚轮）→ 界面响应 → 信号发射 → 哪个 Manager 接收
   - 用流程图或文字描述，标注关键决策点
3. **信息架构**：
   - 界面显示什么数据？数据从哪个 CSV 来？
   - 标注 "数据来源：XXX.csv 的 YYY 列"
4. **异常分支**：
   - 数据为空时显示什么？
   - 操作失败时提示什么？
   - 非法操作时怎么阻止？

**人机分工**：AI 逐个界面设计 → 人类逐个界面确认。

**产出**：交互需求文档，可填入功能规划模板的 §3「交互方式」+ §4.6「交互体验」。

---

### 阶段 3：视觉设计 → 方向 + 布局 + Pixso

**目标**：确定每个 UI 界面的视觉方向——基调、氛围、布局、关键视觉元素。

**输入**：UI 场景清单 + 交互需求 + 现有 UI 风格体系（参考 `开仙门-美术绘制规范-v2.md` 的色彩/字体/间距规范）。

**步骤**：

1. **风格对齐**：
   - 确认与现有 UI 风格一致（暗色修仙基调、金色高亮、阿里巴巴普惠体）
   - 如需要新风格方向，明确描述差异点和理由
2. **视觉方向描述**（每个界面）：
   - 基调/氛围（庄重/轻快/紧张/神秘）
   - 主色调和辅助色
   - 关键视觉元素（标题区/主视觉区/交互热区/装饰元素）
3. **布局描述**（文字或 Pixso）：
   - 用文字描述布局结构（"顶部标题栏 + 中部卡片网格 + 底部按钮栏"）
   - 可选：用 Pixso 出视觉稿（通过在"界面原型草图"页面新建 Frame）
   - 标注关键尺寸（界面整体尺寸、核心元素的位置和大小）
4. **字体与排版**：
   - 字号阶梯、行高、对齐方式
   - 与现有字体规范对齐

**Pixso 操作参考**：

> GAME-002 的 Pixso 设计稿放在「界面原型草图」页面，每个界面一个顶层 Frame。
> - 新建 Frame：在 Pixso 中创建，或通过 `code_to_design` 从 HTML 原型导入后重命名
> - 读取设计稿：AI 通过 `query_nodes` 读取 Frame 的结构化数据
> - 图层命名：遵循 [GAME002-UI层命名规范](GAME002-UI层命名规范.md)（`ScreenName → Bg → Root → 组件 → 元素`）
> - 导入后必须执行图层重命名（`apply_design` 批量 `U()`），将 `div`/`p` 等 HTML 标签名替换为规范名称
> - 此阶段只做视觉设计，不涉及资产导出

**产出**：视觉方向文档 + 可选的 Pixso 布局 Frame。

**判断标准**：人类看完能说"这个方向是对的，可以往下拆资产了"。

---

### 阶段 4：资产拆解 → 美术资产清单

**目标**：把视觉方向转化为可执行的美术资产清单——每个资产有明确规格、优先级、来源。

**输入**：视觉方向文档 + 交互需求。

**步骤**：

1. **逐界面拆解**，按类型分组：

| 资产类型 | 包含 | 示例 |
|---------|------|------|
| **UI 元素** | 底板、边框、按钮（3 态）、卡牌框、面板背景 | 卡牌底板 200×280、确认按钮 120×40 |
| **图标** | 功法图标、山峰图标、道具图标、状态图标 | 功法图标 80×80、山峰图标 128×128 |
| **插图/原画** | 角色立绘、场景图、全屏背景、宣传图 | 百世书器灵立绘、山峰全景图 |
| **动画帧** | 精灵表、角色动画帧、序列帧 | 敌人待机精灵表、器灵形态切换帧 |
| **VFX** | 粒子特效、过渡动画、光效 | 卡片选中光晕、界面切换过渡 |
| **SFX** | UI 音效、技能音效、环境音 | 按钮点击音效、卡片翻转音效 |

2. **每个资产填规格表**：

| # | 资产 | 类型 | 尺寸 | 格式 | 色彩/风格约束 | 优先级 | 来源 |
|---|------|------|------|------|-------------|--------|------|
| A1 | 器灵选择背景 | 全屏贴图 | 1280×720 | PNG | 深色云海，星光粒子 | P1 | AI 生成 |
| A2 | 百世书卡片 | 图标+底板 | ~200×300 | PNG | 金色边框，古书居中 | P0 | AI 生成 |
| ... | ... | ... | ... | ... | ... | ... | ... |

3. **标注优先级**：
   - **P0**：上线必须，没有它功能不可用
   - **P1**：首版可用代码占位，正式版必须有
   - **P2**：锦上添花，有更好没有也行

4. **标注资产来源**：
   - **AI 生成**：走 asset-pipeline（Lovart）生产
   - **复用现有**：已有资产可直接使用
   - **代码绘制**：用 ColorRect/Label/StyleBoxFlat 纯代码实现

5. **A/V/S 编号**：A=Asset（静态资产），V=VFX（特效），S=SFX（音效）。编号确保每个资产可被精确引用。

**产出**：美术资产清单（可直接填入功能需求模板 §7-附，或同步到美术绘制规范 §7 资产清单）。

**判断标准**：asset-pipeline 拿到这份清单能直接开始生产——每个条目都有明确的 Prompt 方向。

---

## 最终产出：美术需求文档

4 阶段走完后，汇总为一份完整的美术需求文档：

```
1. UI 场景清单        ← 阶段 1：有哪些界面
2. 交互需求           ← 阶段 2：每个界面怎么交互
3. 视觉方向           ← 阶段 3：每个界面长什么样
4. 美术资产清单       ← 阶段 4：需要生成哪些资产
   4.1 UI 元素
   4.2 图标
   4.3 插图/原画
   4.4 动画帧
   4.5 VFX
   4.6 SFX
5. 优先级汇总         ← P0/P1/P2 统计
```

这份文档的各个部分可**直接填入**现有模板的对应章节：

| 美术需求文档章节 | 映射到模板 |
|-----------------|-----------|
| 1. UI 场景清单 | 功能规划 §2「界面描述」补全 |
| 2. 交互需求 | 功能规划 §3「交互方式」+ §4.6「交互体验」 |
| 3. 视觉方向 | 功能规划 §4.1-4.5「美术与体验需求」细化 |
| 4. 美术资产清单 | 功能需求 §7-附「美术与体验需求」+ 美术绘制规范 §7 |
| 5. 优先级汇总 | 美术绘制规范 §7 汇总表 |

## 约束与规则

- **入口是策划文档，不是引擎代码**：不从 Godot 工程反推需求
- **设计阶段不碰引擎**：产出美术需求文档即完成任务，引擎实现由下游流程负责
- **风格对齐现有体系**：视觉方向必须参考 `开仙门-美术绘制规范-v2.md` 的色彩/字体/间距规范
- **资产可执行**：阶段 4 产出的每个资产条目必须有足够信息支撑 asset-pipeline 生产
- **人类是审美终裁**：所有视觉判断（好不好看、方向对不对）由人类决定
