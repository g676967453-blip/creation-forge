# 写策划案 — HTML 格式 v0.1

> **定位**：轻量级功能策划案工作流。一份 HTML = 完整策划案，替代重流程的 4 份 Markdown。
> **版本**：v0.1 | 2026-07-29 | 状态：**半成品（可用，持续迭代中）**
> **适用场景**：中小功能（≤5 界面、≤20 资产）。大型功能走 [功能开发-流水线](功能开发-流水线.md)。

## 1. 这是什么

一个自包含的 HTML 文件，浏览器打开即可阅览完整策划案。5 个一级页签覆盖功能全流程，策划 + AI 协作填充。

**核心理念**：

> 一份 HTML 就是一份策划案——人看得懂，机器读得动。

**设计原则**：

| 原则 | 说明 |
|------|------|
| **一站式** | 不拆多份文件，一个 HTML 装下全部信息 |
| **双重可读** | 浏览器打开给人看；`<meta>` + `<script type="application/json">` 给机器解析 |
| **策划友好** | 功能规则用 Excel 层级格式（● → 一./1./1）/①），匹配策划既有习惯 |
| **可交互** | 动态交互 tab 做可点击的功能模拟，不用进引擎就能验证交互逻辑 |
| **零依赖** | 纯 HTML+CSS+JS，无外部库，离线可用 |

**一份 HTML 同时服务三个下游**：

| 下游 | 用法 |
|------|------|
| 人类（策划/美术/程序） | 打开浏览器看效果，确认交互逻辑和功能范围 |
| AI（后续协作） | 解析 `<meta>` 标签和结构化 JSON，提取功能规格 |
| 程序员 | 界面说明 tab 的编号锚点 → 直接对应 UI 场景节点 |

## 2. 与重流程的关系

```
                    用户想法
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
    小功能（≤5界面）  中等功能      大型功能
          │            │            │
          ▼            ▼            ▼
    本流程 v0.1     本流程先行    完整 4 阶段流水线
    (HTML 策划案)   再补需求文档   (功能开发-流水线)
```

| | 本流程（轻量） | 完整流水线（重量） |
|---|---|---|
| **交付物** | 1 份 HTML | 4 份 Markdown + HTML 原型 + 资产清单 |
| **适用** | ≤5 界面、≤20 资产 | 复杂系统、多模块联动 |
| **耗时** | 1-2 轮对话 | 4-8 轮对话 |
| **人类确认** | 2 次 | 4 次（每阶段 1 次） |
| **资产拆解** | 表格列出（嵌入 HTML tab 5） | 独立 A/V/S 编号清单 |
| **技术规格** | 不涉及（直接口述给 AI 写代码） | 完整信号契约 + 三层归属 + 反模式自查 |

**混用策略**：
- 先用本流程快速出案 → 人类确认方向 → 需要时补完整需求文档（阶段 2）
- 大型功能的子模块可以各走本流程，主骨架走完整流水线

## 3. 5 页签结构

```
┌─────────────────────────────────────────────────────────┐
│ [功能简介] [功能规则] [界面说明] [动态交互] [资产需求]     │
├─────────────────────────────────────────────────────────┤
│ 当前选中 tab 内容                                        │
│                                                         │
│ 资产需求 tab 包含 5 个二级页签：                          │
│   [UI] [原画] [动作] [特效] [3D资产]                     │
└─────────────────────────────────────────────────────────┘
```

### Tab 1：功能简介

| 内容块 | 说明 |
|--------|------|
| 文档信息 | 功能名称、版本、日期、策划人、状态 |
| 变更日志 | 更新人、时间、内容（表格） |
| 关联 CSV | 涉及的配置表及操作类型（读/写） |
| 功能定位 | 一句话 + 在游戏流程中的位置 |
| 不在范围内 | 明确排除项，防范围蔓延 |
| 颜色图例 | 黄色=未定案、绿色=改动标注、蓝色=系统提示、红色=强调 |

### Tab 2：功能规则

**写法规范**：Excel 层级格式，匹配策划既有习惯。

```
● 活动简述          ← 绿色底线标题
  一. 功能概述       ← 一级缩进
    1. 子项          ← 二级缩进
      1）细项         ← 三级缩进
      ① 更细项        ← 四级缩进
  示意：举例          ← 灰色示例
```

**规则**：
- 直接陈述事实，不写"应该""可能""大概"
- 标注 `<span class="text-blue">支持配置</span>` 表示数值走 CSV
- 不确定的内容用 `<span class="mark-yellow">黄色标记</span>`

### Tab 3：界面说明

**布局**：左图右文（16:9 原型框 + 编号锚点）。

```
┌──────────────────────────┐  ┌─────────────────────┐
│                          │  │ ① [功能板块名称]      │
│     [界面原型 16:9]       │  │   功能效果、交互规则、  │
│         ①                │  │   多种状态描述         │
│                          │  │                      │
│                          │  │ ② [功能板块名称]      │
│                          │  │   ...                │
└──────────────────────────┘  └─────────────────────┘
```

**右侧说明写什么**：
- ✅ 功能效果、交互规则、多种状态（默认/选中/禁用/空/完成）
- ❌ 不写美术尺寸、颜色、字体规格（那是美术需求文档的事）

**左侧编号锚点**：黄色圆圈数字，标注界面上的关键交互区域，与右侧说明一一对应。

### Tab 4：动态交互

可点击的功能模拟。包含完整状态机：

```
idle → showing（入场动画）→ selecting（用户操作）→ done（退场动画）
```

**技术要求**：
- 纯 CSS + JS，无外部依赖
- 支持入场动画、交互反馈、退场过渡
- 有"重新开始"按钮重置状态
- 覆盖正常流程，不要求覆盖所有异常分支

### Tab 5：资产需求

5 个二级 tab，每类一张表格：

| 二级 tab | 编号前缀 | 表格列 |
|----------|---------|--------|
| **UI** | U | 编号/名称/类别/规格/格式/数量/优先级/Prompt方向 |
| **原画** | C | 编号/名称/类别/规格/格式/数量/优先级/Prompt方向 |
| **动作** | M | 编号/名称/类别/规格/帧数/FPS/优先级/触发说明 |
| **特效** | V | 编号/名称/类别/触发/表现/时长/优先级/实现方式 |
| **3D资产** | D | 编号/名称/类别/面数/格式/贴图/优先级/用途说明 |

**优先级**：

| 级别 | 含义 | 标签样式 |
|------|------|---------|
| P0 | 上线必须，没有它功能不可用 | 红色 tag |
| P1 | 首版可用代码占位，正式版必须有 | 黄色 tag |
| P2 | 锦上添花，有更好没也行 | 绿色 tag |

## 4. 执行步骤

### 步骤 1：复制模板

```
复制 docs/workflows/templates/功能策划案-HTML模板.html
     → projects/{项目}/策划文档/03-功能规格/{日期}-{功能名}/{日期}-{功能名}-功能策划案.html
```

### 步骤 2：AI 读取上下文

AI 读取：
- 项目的 GDD / 设计文档（了解整体游戏框架）
- 相关现有功能的策划案（了解既定模式）
- 涉及的 CSV 配置表（了解数据结构）

### 步骤 3：逐 tab 协作填充

AI 主导填充，人类逐 tab 确认：

| 顺序 | Tab | AI 做什么 | 人类确认什么 |
|------|-----|----------|------------|
| 1 | 功能简介 | 填文档信息、功能定位、排除项 | 范围对不对 |
| 2 | 功能规则 | 按 Excel 层级格式写规则 | 规则有没有遗漏 |
| 3 | 界面说明 | 画原型布局、写交互说明 | 界面全不全、交互对不对 |
| 4 | 动态交互 | 写状态机 + JS 交互代码 | 流程走不走得通 |
| 5 | 资产需求 | 逐界面拆资产、填规格 | 优先级和数量 |

### 步骤 4：浏览器验证

人类用浏览器打开 HTML 文件：
- [ ] 5 个 tab 正常切换
- [ ] 动态交互可点击跑通
- [ ] 资产表格信息完整
- [ ] 颜色标注正确

### 步骤 5：定稿

确认无误 → 状态改为"已定案" → 提交 Git。

## 5. 人机分工

| 步骤 | 人 | AI |
|------|-----|-----|
| 1. 想法描述 | 用一句话说清要什么功能 | 倾听，参考现有系统 |
| 2. 范围澄清 | 回答 AI 的澄清问题 | 提 5-8 个关键问题：触发时机？涉及系统？明确不做什么？ |
| 3. Tab 1-2 填充 | 确认功能和规则 | 填功能简介 + 功能规则 |
| 4. Tab 3 填充 | 确认界面和交互逻辑 | 画原型布局 + 写交互说明 |
| 5. Tab 4 填充 | 确认交互流程 | 写状态机 + JS 代码 |
| 6. Tab 5 填充 | 确认资产范围和优先级 | 拆资产 + 填规格表 |
| 7. 最终确认 | 浏览器验证，逐 tab 检查 | 修正争议点 |

**核心原则**：

| | 人 | AI |
|---|---|---|
| **职责** | 决策者：确认范围、判断交互、拍板优先级 | 执行者：填模板、写代码、拆资产 |
| **不能替代** | 审美判断、游戏直觉、业务理解 | 信息整理、模板填充、边界条件穷举 |

## 6. 颜色标注约定

| class | 效果 | 用途 |
|-------|------|------|
| `.mark-yellow` | 黄色背景 | 未定案/待讨论（定案后清除） |
| `.mark-green` | 绿色背景 | 定案后改动标注，须带日期 |
| `.text-blue` | 蓝色文字 | 邮件、系统提示文字、支持配置项 |
| `.text-red` | 红色文字 | 强调、需重点关注 |

> 颜色图例写在 Tab 1 底部，确保任何打开 HTML 的人都知道含义。

## 8. 人类确认点

流程中设 **2 个确认点**：

| # | 时机 | 看什么 | 决策 |
|---|------|--------|------|
| **确认 1** | Tab 1-2 填充完后 | 范围对不对、规则有没有遗漏 | 继续 / 修改 / 放弃 |
| **确认 2** | 全部 5 个 tab 填充完后 | 浏览器打开，切 tab，跑交互，查资产表 | 定稿 / 修改 |

> 比完整流水线少 2 次确认（去掉了独立的需求确认和资产确认），因为轻量功能的复杂度不需要那么细粒度的卡点。

## 9. 约束与规则

- **一份 HTML 就是全部**：不拆多份文件，不要求配套 Markdown
- **先功能后美术**：Tab 1-4 确认完毕再填 Tab 5，不提前拆资产
- **规则写法匹配策划习惯**：Excel 层级格式 > Markdown 卡片格式
- **界面说明不写美术数值**：右侧只写功能和规则，尺寸/颜色/字体留给资产表格
- **动态交互覆盖正常流程即可**：不要求穷举异常分支（那是代码实现的事）
- **颜色标注是临时标记**：定案后清除所有 `.mark-yellow`
- **模板是骨架，不是牢笼**：覆盖 80% 的情况，特殊情况可以增删内容块
- **人可以中途叫停**：任何时候觉得方向不对，回到步骤 1

## 10. 已知待改进

> v0.1 标记为「半成品」，以下问题在后续版本迭代：

| # | 问题 | 影响 | 计划 |
|---|------|------|------|
| 1 | 模板为通用空白骨架，实例包含完整 CSS/JS，两份代码未统一 | 改模板后需手动同步实例 | v0.2：合并为一份可配置模板 |
| 2 | 动态交互的状态机代码内联在实例中 | 每次写交互都要重写 JS | v0.2：抽取为通用交互函数库 |
| 3 | 缺少 SKILL 文件 | 无法一键触发 `/写策划案` | v0.2：建立 SKILL |
| 4 | 颜色标注 class 只在模板 `<style>` 中定义 | 实例可能遗漏样式 | v0.2：确保模板 CSS 完整自包含 |
| 5 | 资产需求表格列项因项目类型不同需要调整 | 3D 项目不需要 3D tab | v0.2：模板支持按项目类型显隐二级 tab |
| 6 | `<meta>` 和结构化 JSON 未定义具体 schema | 机器可读停留在口号 | v0.3：定义 JSON schema |
