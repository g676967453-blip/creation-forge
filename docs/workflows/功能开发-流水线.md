# 功能开发-流水线

> 版本：v2 | 最后更新：2026-07-28 | 对应 SKILL：待建
> v2 变更：合并 GAME002-UI制作 的模板映射表 + GAME002-功能开发 的数据原则和实现后步骤

## 触发条件

用户提出一个需要从头设计的新游戏功能，且该功能涉及 UI 界面和美术资产。

典型触发语句：
- "做一个 XXX 功能"
- "设计 XXX 系统"
- "加一个 XXX 界面"
- "从零画 XXX 的资产"

**不适用场景**（走其他工作流）：
- 纯 Bug 修复 → 直接改代码
- 纯数值调整 → 改 CSV，不走流水线
- 已有功能的 UI 微调 → 跳过阶段 1、2，从阶段 3 进入
- 已有资产清单的追加生产 → 直接走阶段 4 或 [道具图标-生产](道具图标-生产.md)

## 这是什么

独立游戏功能开发的标准流水线。一个功能从想法到可执行资产，走完 4 个阶段：

```
用户想法 → 功能策划 → 功能需求 → 界面交互UI → 美术资产
                ↓          ↓           ↓           ↓
            策划文档    技术规格    美术需求文档   资产清单
```

每个阶段是一个独立子 SOP，可单独引用执行。4 阶段走完后，代码和资产两条线并行启动。

│                  │                  │                  │

│                  │                   │ ② 交互设计        │ P0/P1/P2 分级
│                  │                   │ ③ 视觉设计        │ 标注来源
│                  │                   │ ④ 资产拆解        │
│                  │                   │                   │
▼                  ▼                   ▼                   ▼
┌──────────────────┼───────────────────┼───────────────────┼──────────┐
│ 策划文档          │ 需求文档           │ 美术需求文档        │ 资产清单  │

## 4 阶段速览

| 阶段 | 做什么 | 核心问题 | 人确认什么 | 子 SOP |
|------|--------|---------|-----------|--------|
| 1. 功能策划 | 把想法变成结构化策划文档 | 玩家看到什么？怎么操作？ | 范围对不对、界面全不全 | [01-功能策划](01-功能策划.md) |
| 2. 功能需求 | 把策划文档翻译成技术规格 | 涉及哪些模块？数据怎么流？ | 信号设计、CSV 结构、模块影响 | [02-功能需求](02-功能需求.md) |
| 3. 界面交互UI | 把技术规格转化为视觉设计 | 每个界面什么状态？怎么交互？长什么样？ | 交互逻辑、视觉方向 | [03-界面交互UI](03-界面交互UI.md) |
| 4. 美术资产 | 把视觉设计拆成可执行资产条目 | 每个资产什么规格？谁来做？优先级？ | 优先级、AI 生成的 Prompt 方向 | [04-美术资产](04-美术资产.md) |

## 运行规则

### 串行衔接：上游不确认，下游不开工

```
阶段 1 确认完毕 → 才能进入阶段 2
阶段 2 确认完毕 → 才能进入阶段 3
阶段 3 确认完毕 → 才能进入阶段 4
```

每个阶段的**产出物**是下游的**唯一入口**。下游不允许绕过上游产出物直接从代码/引擎反推需求。

### 人机分工核心原则

| | 人 | AI |
|---|---|---|
| **职责** | 决策者：确认范围、审核架构、判断视觉、拍板优先级 | 执行者：读文档、填模板、设计流程、拆资产 |
| **不能替代** | 审美判断、游戏直觉、业务理解 | 信息整理、模板填充、边界条件穷举 |

### 阶段跳过规则

| 场景 | 允许跳过 |
|------|---------|
| 纯数据/配置改动（不改 UI） | 阶段 3、4 |
| 纯 UI 调整（不改逻辑） | 阶段 2（从阶段 1 直跳阶段 3） |
| 纯资产生产（不改功能） | 阶段 1、2、3（从资产清单直入阶段 4） |

## 阶段 3 产出映射（设计文档 → 模板章节）

阶段 3（界面交互UI）走完 4 个子阶段后，产出的美术需求文档各部分可以直接填入策划模板的对应章节：

| 美术需求文档章节 | 映射到模板 |
|-----------------|-----------|
| 1. UI 场景清单 | 功能规划 §2「界面描述」补全 |
| 2. 交互需求 | 功能规划 §3「交互方式」+ §4.6「交互体验」 |
| 3. 视觉方向 | 功能规划 §4.1-4.5「美术与体验需求」细化 |
| 4. 美术资产初稿 | 功能需求 §7-附「美术与体验需求」 |

> 这意味着阶段 3 的产出不是"另一份文档"，而是把策划模板里描述不清的 UI 章节**填实**。

## 数据设计原则

在阶段 2（功能需求）定义数据结构时，遵循：

- **配置表是唯一真相**：数值以 CSV/JSON/Resource 为准，文档描述引用配置表，不重复定义
- **数据不写死在代码里**：数值、掉落表、技能参数等全部走配置，代码只读配置不定义值
- **改数值 = 改配置表**：不需要重新编译或改代码
- **文档描述引用配置**：需求文档中写"详见 `xxx.csv` 的 `yyy` 列"，不抄数值

## 阶段 4 之后：进入实现

4 阶段走完，设计工作完成。代码和资产两条线并行启动：

```
[资产清单] ──→ asset-pipeline / 外包绘制 ──→ 素材导入引擎
[需求文档] ──→ 代码实现 ──→ 引擎测试 ──→ 文档同步
```

### 代码实现（引擎相关）

- 按需求文档写代码，不绕过文档从引擎反推
- 涉及 UI 时，场景文件按项目命名规范创建（GAME-002 见 [UI层命名规范](../../projects/GAME-002/程序规则/UI层命名规范.md)）
- 新增模块先搭骨架（空场景 + 空脚本），验证通过后再填逻辑

### 测试验证

- 人在引擎中运行，发现问题告知 AI，AI 修复
- 优先验证：核心循环跑通 → 边界条件 → 异常分支

### 文档同步

- 代码改完后，检查关联文档是否需要同步更新
- **改了代码没改文档 = 制造谎言**：后续 AI 读文档会按过时的设计干活
- 同步范围：功能规划、功能需求、CSV 注释、引擎 Wiki（如有）

## 引擎特化版

本流水线是**通用版**。各引擎按本文档 4 阶段走完设计后，进入各自的引擎实现阶段（见下方「阶段 4 之后」）。

## 约束与规则

- **串行严禁跳跃**：上游未确认，下游不得开工
- **入口是文档，不是代码**：每个阶段的输入必须是上一阶段的产出文档
- **配置表是唯一真相**：数值以配置表为准，代码和文档都引用它
- **改了代码必须同步文档**：不传文档 = 制造谎言
- **人可以叫停任何阶段**：任何时候觉得方向不对，回到上一阶段重来
- **模板是骨架，不是牢笼**：模板覆盖 80% 的情况，特殊情况可以增删章节
- **阶段 3 和 4 可以合并**：小功能（≤3 个界面）可以边设计视觉边拆资产
