# 2026-07-28 流水线规范体系搭建

---

## 遇到了什么

用器灵界面跑通功能开发流水线后，暴露出三个系统性缺口：

1. **策划案模板不够用**：现有模板把程序需求、数值需求、美术需求揉在一份文档里，导致美术浅尝辄止、数值散落各处
2. **HTML 原型没有设计规范**：两个原型（开场黑幕 vs 器灵选择）用完全不同的配色/字体/间距，每次都从零画 CSS
3. **Lovart 生成没有视觉约束**：纯文字 prompt 导致布局跑偏、风格不统一，v2 和 v3 的对比证明了"有量化规范 = 可预期，没有 = 靠运气"

## AI 怎么协作的

### 阶段 1：跑通流水线，定位缺口

- 走完器灵界面的完整链路：策划案 → 需求 → UI 设计 → HTML 原型 → Lovart 生成 → 引擎对照
- 产出：[器灵选择-美术需求.md](../projects/GAME-002/美术制作/01-原画需求/UI/器灵选择-美术需求.md)（18 项资产清单 + 19 项引擎差异对照）
- 产出：[流水线跑通报告](2026-07-28-器灵界面流水线跑通.md)

### 阶段 2：Lovart 生成三轮迭代，验证参考图方案

- v1：纯文字 → 布局完全跑偏
- v2：修仙配色 prompt → 风格对了但布局仍然不对
- v3：**HTML 原型截图做参考图** → 布局对齐度大幅提升
- 关键认知：AI 生图模型对纯文字布局描述的理解不可靠，必须用参考图约束

### 阶段 3：HTML 原型重设计

- 按用户要求改为黑白灰极简配色 + 补齐游戏组件（道具框/技能框/插图占位）
- 新增品质色体系（普通/稀有/史诗/传说）
- 道具框底板灰色 + 品质颜色边框区分稀有度
- 名称移到框外

### 阶段 4：搭建三套规范体系

**讨论点 1 — 策划案拆分**：功能策划案 → 三份独立文档（程序功能需求 / 策划数值需求 / 美术体验需求），各司其职

**讨论点 2 — HTML 设计规范**：三位一体
- [开仙门-UI设计规范.md](../projects/GAME-002/美术制作/开仙门-UI设计规范.md) — CSS Token 定义（颜色/字体/间距/圆角/阴影，含完整 CSS 变量速查表）
- [开仙门-UI组件库.html](../projects/GAME-002/ui-prototypes/开仙门-UI组件库.html) — 可渲染组件展示页
- [_template.html](../projects/GAME-002/ui-prototypes/_template.html) — 原型起始模板

**讨论点 3 — Lovart 视觉约束**：四件套
- UI 色板参考图（PNG，Lovart 可直接引用）
- UI 界面 Prompt 模板（§4.9）
- 风格关键词白名单（✅允许 / ❌禁止）
- 标准生成工作流（HTML截图→上传→附件→chat）

## 视频生产草案

### 第一幕：遇到了什么问题

- 核心问题：功能开发的流水线跑通了，但每次做新界面都要从零开始——HTML 原型没有设计规范、Lovart 生成没有约束、策划案和需求文档结构不统一
- 为什么是问题：三个缺口导致每次做功能都在"重新发明轮子"，效率低、风格不统一、AI 生成结果不可预期
- 如果没有 AI：传统做法是设计团队提前制定 Design System 和组件库，但独立开发者往往跳过这一步，导致越做越乱

### 第二幕：AI 怎么协作解决的

- 先跑通一个完整案例（器灵界面），暴露所有问题
- 三轮 Lovart 迭代验证了一个关键结论：AI 生图需要参考图约束布局
- 然后从案例中抽象出三套规范，不是凭空设计，而是从实战中提炼
- HTML 组件库是可渲染的——打开浏览器就能看到所有组件的实际效果，复制 CSS 直接可用
- 最终形成闭环：策划模板 → HTML 原型（有 token 约束）→ Lovart 生成（有参考图+色板+Prompt 模板约束）

### 第三幕：效果展示

- 展示规范体系的文件结构图
- 展示 UI 组件库页面的实际渲染效果
- 对比 Lovart v1（跑偏）vs v3（对齐）的生成结果
- 演示用 `_template.html` 快速创建新原型的过程
- 核心认知：**规范不是写出来的，是从实战案例中提炼出来的**

### 一句话总结（金句候选）

> 好的 AI 协作不是让 AI 猜你要什么，而是给 AI 一套"设计宪法"——色彩、间距、布局都有了明确的法律条文，它就不再越界。
