# 2026-07-29 竖版手游交互原型图规范 v1.0

---

## 📋 问题解决日志

### 遇到了什么

做竖版手游（开仙门等）时，交互原型图没有统一标准——按钮多大、放哪里、手势怎么定义、弹窗什么规格、颜色怎么选——每次都是凭感觉，出来的原型图风格不统一，没法形成可复用的生产线标准。

### AI 怎么协作的

1. **确立方法论锚点**：以网易游戏「信·达·雅」交互设计体系为核心框架，参照阴阳师、梦幻西游、倩女幽魂、逆水寒、哈利波特：魔法觉醒等一线手游的交互实践。
2. **结构梳理**：从 0 到 1 搭建 17 章规范体系——画布安全区 → 拇指热区 → 手势系统 → 触控规格 → 布局系统 → 网格系统 → 基础组件 → 导航 → 状态反馈 → 弹窗 → 动效 → 排版 → 色彩 → 音效 → 横竖屏 → 可访问性 → 交付清单。
3. **可视化原型**：每个规范点都配 CSS 绘制的手机原型示意（等比缩放的 375×667 手机框），包括安全区标注、四区拇指热力图、五种屏幕模板（大厅/战斗/列表/弹窗/卡片选择）。
4. **组件规范落地**：定义了按钮（四级体系）、卡片（四级品质+三态）、槽位、Tab、Badge、文字阶梯、进度条等 8 类基础组件的精确尺寸和交互规则。
5. **单文件 HTML 交付**：整个规范是一份自包含的 HTML 文件，浏览器打开即可阅读所有规范+原型示意，无需任何构建工具。

### 产出结果

- **交互规范文档**：[docs/specs/vertical-game-interaction-spec.html](../docs/specs/vertical-game-interaction-spec.html)
  - 17 章规范 + 附录速查表 + 修订记录
  - 5 套手机布局模板（CSS 绘制原型图，非图片）
  - 8 类基础组件规范（精确到像素的尺寸+颜色+状态）
  - 1 份交付检查清单（16 项逐条检查）
  - 基准分辨率 750×1334，适配 750×1624

## 🎬 视频生产草案（三幕结构）

### 第一幕：遇到了什么问题

- 核心问题：做游戏原型图时没有统一的交互标准，每次都是"我觉得按钮放这里差不多""弹窗大概这么大吧"——同一个项目的不同页面看起来像不同游戏。
- 为什么这是个问题：交互规范不是一次性的设计稿，而是生产线的标准化基础。没有规范 = 重复造轮子 = 交付品质不可控。
- 如果没有 AI 会怎样：需要一个人花至少 2-3 天去调研网易系手游的交互方案、整理 17 个维度的规范、手绘所有原型示意图、排版成可交付的文档。

### 第二幕：AI 怎么协作解决的

- 我是这样问 AI 的：设计一份竖版手游交互原型图规范，以网易信达雅体系为方法论，覆盖从画布到动效到交付清单的全流程。
- AI 给了什么方案：直接用 HTML+CSS 在浏览器里呈现完整规范——左边是文字规范，右边是 CSS 绘制的手机原型示意。所有视觉示例都是代码生成的，不依赖任何外部图片。
- 中间有什么调整/追问：多次迭代了组件尺寸（按钮四级的精确 px 值）、拇指热区的四区划分从三区扩展、品质色需要同时用颜色+文字+边框区分以保障色觉障碍用户。
- 最终方案是什么：一份 680 行的单文件 HTML，17 章规范 + 5 套布局原型 + 8 类组件规范 + 检查清单，无任何外部依赖。

### 第三幕：效果展示

- 最终效果：打开 HTML 文件 = 一本完整的交互规范手册。每个规范都有「为什么」（网易标杆参考）+「怎么做」（精确尺寸+颜色代码）+「长什么样」（手机原型示意）。
- 演示方式：浏览器截图 + 规范文档目录展示
- 学到的关键点：好的规范不是约束创造力，而是把重复决策自动化，让人把精力花在真正需要创造的地方。

### 一句话总结（金句候选）

> **交互规范不是限制设计，而是把「按钮放哪」这种重复决策交给标准，把创意留给真正重要的事。**
