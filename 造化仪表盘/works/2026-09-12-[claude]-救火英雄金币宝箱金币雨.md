## 📋 问题解决日志

### 遇到了什么

需求原文：**「增加一个金币宝箱道具，接住宝箱后，进入金币雨小游戏，背景 40% 透明的黑幕，天上疯狂掉金币雨，10 秒钟，玩家用蹦床去接，到了就算。」**

要做的是「接住一个道具 → 切入一个临时小游戏 → 再切回来」这种**子模式**，而项目原有的状态机只有 MENU/PLAYING/LEVELUP/OVER/PAUSE 五态，没有一个能表达「还在游玩中，但玩法换了一套」。

### AI 怎么协作的

**关键判断：不新增 State。**

第一反应是加 `State.COINRAIN`，但查 `main_ui.gd:134` 发现：

```gdscript
var playing: bool = s == game.State.PLAYING
if vpad_left:  vpad_left.visible  = playing
if vpad_right: vpad_right.visible = playing
if skill_btn:  skill_btn.visible  = playing
```

虚拟方向键和技能键的显隐是**按 `== PLAYING` 硬判**的。新增状态会让玩家在金币雨里**失去左右移动能力**——而金币雨恰恰要求用蹦床接金币。于是改用 `_coin_rain_active` 标志位，`state` 保持 PLAYING，UI 完全不受影响。

**复用而非新造**：
- 球冻结直接用已有的 `ball.freeze_motion()` / `unfreeze_motion()`（原本给暂停用），暂停/恢复语义天然正确
- 金币图标复用已有 `assets/pixel/ui/ui_icon_coin.png`（64×64 真实插画），不另造美术
- 接取判定盒沿用 `item.gd` 的 `CATCH_Y_MIN/MAX` + `CATCH_X_PAD`，玩家直觉一致
- 暂停安全免费获得：`_process` 首行 `state != PLAYING` 即整体冻结（倒计时也停）

**踩到的坑**：新增 `class_name CoinRain` 后 headless 直接报 `Could not find type "CoinRain"`——`.godot/global_script_class_cache.cfg` 是导入期产物，新类必须先 `--import` 才进缓存。不是代码问题。

**黑幕的层级怎么保证**：CoinRain 是运行期 `add_child` 到 GameRoot 的**最后一个子节点**，所以它的 40% 黑幕天然画在背景/砖块/蹦床/球之上；金币（`z_index=1`）与倒计时 Label（`z_index=2`）再画在黑幕之上。冒烟里用 `rain_is_last_child` 把这条不变量钉住了。

**踩到的第二个坑（Web 专属）**：倒计时 Label 在 GameRoot 空间下，**拿不到 HUD 的 Theme**。项目之前修过「Web 中文变方框」——Web 导出没有系统中文字体。所以 Label 必须自带 `ui_theme.tres`，否则手机上倒计时会显示成方框。已用 `label_has_theme` 断言守住。

## 🎬 视频生产草案（三幕结构）

### 第一幕：遇到了什么问题

给弹球游戏加一个「接住宝箱就进小游戏」的奖励关卡。听起来是加个道具，实际难点是：**游戏的整个状态机里，没有一格能装下「还在玩，但玩法换了一套」**。

- 核心问题：临时子模式没有位置安放
- 为什么这是个问题：最直觉的做法是加一个新状态，但会连带打断一堆按状态硬判的 UI
- 如果没有 AI 会怎样：加个 `State.COINRAIN`，跑起来发现虚拟按键全没了，再回头一层层查为什么

### 第二幕：AI 怎么协作解决的

- **我是这样问 AI 的**：直接给了完整规则（宝箱 → 40% 黑幕 → 金币雨 → 10 秒 → 蹦床接）
- **AI 给了什么方案**：先去读状态机的**消费方**再决定要不要扩状态——在 `main_ui.gd:134` 找到 `playing = (s == PLAYING)`，判断出「新增状态会没收玩家操作权」，改用标志位
- **中间有什么调整/追问**：写完先跑 headless，报 `Could not find type CoinRain` → 发现是新类没进导入缓存，`--import` 解决；冒烟第一遍 29/30，失败项是**测试断言自己写错了**（`_spawn_timer` 初值 0 导致首帧也会生成金币，数量应为 ≥1）
- **最终方案是什么**：标志位 + 复用冻结/图标/判定盒，30/30 通过，无回归

### 第三幕：效果展示

- **最终效果**：灭掉火砖有概率掉金币宝箱 → 接住 → 全场压 40% 黑幕 → 金币疯狂坠落 → 蹦床接住即加分 → 10 秒后黑幕散去、球解冻继续
- **演示方式（截图/GIF/屏幕录制）**：F5 录屏接住宝箱到金币雨结束的完整 10 秒
- **学到的关键点**：**要扩状态机之前，先读状态的消费方**。加状态的成本不在写入端，在那些 `==` 硬判的读取端

### 一句话总结（金句候选）

> 加一个新状态之前，先去数一数有多少地方在 `==` 判断旧状态。

## 🔁 v2 迭代（同日，试玩反馈）

用户试玩后追加三条要求，均已实现：

**1）接住金币要回弹 + 跳数值**

- **回弹**：接住瞬间不再立刻消失，而是给一个向上初速（`CATCH_BOUNCE_VY = -320`）+ 重力（`CATCH_GRAVITY = 1150`），画一条抛物线并同时淡出（`CATCH_FADE = 0.42s`）。金币在这段时间留在 `_coins` 里跑动画，不再参与接取判定。
- **跳数值**：复用同一天做的 `FloatText`。数值按连击递增 `1 → 2 → 4 → 8 → 16`（`POP_SERIES`），用户明确说「只是动画效果」，所以**显示值与实际结算完全解耦**，不改数值平衡。

**2）金币要有大有小**

`COIN_SCALE_MIN/MAX = 0.72 ~ 1.35`，每枚金币生成时随机。

一个刻意的设计：**判定盒挂在蹦床上而不是金币上**，所以金币尺寸是纯视觉、不影响手感——大金币不会因此更好接。这是沿用 `item.gd` 的既有约定（判定盒属于蹦床）。

**3）时间到统一结算（流程改动）**

这条把金币从「逐个即时到账」改成了「结束统一结算」，`coin_rain.gd` 因此重构成三段式：

| 阶段 | 行为 |
|------|------|
| `RAIN` | 接住只计数，HUD 不动（不再逐枚入账） |
| `SETTLE` | 大金币从上方落入并回弹 → 数值从 0 快速滚到总量 → 定格 |
| 结束 | `finished(caught, coins, score)` 一次性交给 GameRoot 入账 |

演出细节：
- 数值滚动用**三次方缓出**（先快后慢），收尾变慢才有「要停住了」的期待感，再落定
- 定格动画 = 数字弹一下（`TRANS_BACK` 放大到 1.32 再回正）+ 转金色 + 大金币脉冲
- 层级按需求做成**金币在前面**：大金币 `z_index = 2`，数字 `z_index = 1`，金币压住数字上沿，形成前后层次

冒烟从 30 项扩到 **49 项**，新增覆盖：回弹方向向上、回弹后回收、**当帧不入账**、金币尺寸随机、进入结算、金币在数字前面、滚动中/单调递增/定格、统一个人入账金额精确匹配。

## 🔁 v3 迭代（同日）：修结算版面 —— 数字被金币完全盖住

用户反馈：「金币在前面、数值在后面，目前只看到大金币，数据完全看不到，而且速度很快。」

### 根因是几何遮挡，不是速度

算了一下第一版的版面：

```
数字 Label：position=(0, 185) size=(450,110)，垂直居中 → 字形落在 y 213~267
大金币：  center=(225, 215)，边长 132          → 覆盖 y 149~281
```

**字形 213~267 完全落在金币的 149~281 之内 → 数字被 100% 盖住。**

我当初的想法是「数字从金币两侧露出来」，但把两者都放在画布中心（都参考 `cx`），132px 的金币压在同样居中的数字上，根本露不出来。「速度很快」其实是**看不见**的连带感受——数字本来就基本没显示过。

### 改法：纵向排布 + 放慢

- 数字整体下移到金币下方，只让金币压住**字形顶部约 19px**（层次感还在，数字读得清）
- 新增 4 个版面常量（`SETTLE_CAPTION_Y` / `SETTLE_COIN_CY` / `SETTLE_NUM_CY` / `SETTLE_NUM_H`）集中管理，不再散落 `cx ± N` 的魔法数
- 滚动 `1.1s → 1.8s`，定格停留 `1.0s → 1.4s`
- 数字字号 `74 → 92`

### 回归断言（这条在旧版面上必挂）

`number_not_buried_by_coin` 用版面常量算出「金币纵向区间」与「字形纵向区间」的重叠高度，要求 < 字形高度的 50%。实测验证过它能挡住这个 bug：

| 版面 | 金币区间 | 字形区间 | 被盖 | 上限 | 结果 |
|------|---------|---------|------|------|------|
| 旧 | 149~281 | 213~267 | **53.3px** | 26.6px | **FAIL** |
| 新 | 312~444 | 425~491 | 19.1px | 33.1px | PASS |

另加 `number_glyphs_on_canvas` / `big_coin_on_canvas` 防止版面改到画布外。

**验证：smoke_coinrain 49 → 52 项全过**，五个套件全绿无回归。

## 🔧 调试入口（同日）：右上角「掉宝箱」按钮

宝箱自然掉率约 1.4%/砖（约每 5 关才碰到一次），反复验证金币雨太慢。按项目既有的 `TEST_COIN_BTN_ENABLED` 模式加了一个临时按钮：

| 按钮 | 位置 | 作用 |
|------|------|------|
| `+500 金币`（原有） | 右上角 y46~80 | 加金币 |
| **`掉宝箱`（新增）** | 右上角 y88~122 | 立刻在蹦床正上方掉一个金币宝箱 |

背后是 `GameRoot.debug_drop_chest()`：

- **不走概率、不走权重** —— 直接生成 `Kind.CHEST`
- **`vx = 0` 且落在蹦床正上方** —— 宝箱直线落下、一接就中，不用瞄准
- 游戏未开始 / 金币雨进行中会给提示而不是静默失败

按钮挂 `$Overlays` 顶层（与 +金币按钮一致），主菜单/商店/游戏中都能点。
正式发布把 `TEST_CHEST_BTN_ENABLED` 置 false 即可（`debug_drop_chest()` 可留着，无副作用）。

冒烟加了 4 条：按钮确实挂在 `UI/Overlays/TestChestButton`、调用后场上多出一个宝箱、
宝箱 x 与蹦床对齐、`vx` 为 0 —— 覆盖「按钮点了没反应」这类问题。

**验证：smoke_coinrain 56/56**，五个套件全绿无回归。
